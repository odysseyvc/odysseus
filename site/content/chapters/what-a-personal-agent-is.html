The problem: an assistant that only talks

Suppose you write to an assistant in a chat app: "Find a time next week for lunch with Sam and send him an invite."

A chatbot answers with advice. It might say: open your calendar, look for a free hour around noon, create an event and add Sam as a guest. Every word may be correct, and you still have to do the errand yourself. The chatbot has no way to see your calendar and no way to change it.

What you wanted was different. You wanted the program to look at next week, notice that Wednesday at 12:30 is free, propose it, and then create the event with Sam invited. You also wanted it to ask you once before it emailed Sam, because an invitation goes to another person and cannot be taken back. And if Sam accepts two days later, you would like to be told without having to ask.

That second program is a personal agent. This chapter defines it, fixes the words the rest of the book uses, and sets out what it means for such a program to work. The capabilities that make the errand possible also make harm possible: a program that can send Sam an invitation can send anyone anything.

Four properties of a personal agent

Definitions
Chatbot
A program that answers messages with text. It changes nothing in the world except what appears on your screen.
Agent
A program in which a language model repeatedly chooses an action, sees the result and chooses again, until the task is finished or it gives up.
Personal agent
An agent that works for one person, its owner, inside that person's own accounts, and that keeps working across days rather than within a single conversation.

Four properties separate a personal agent from a chatbot. Each one adds a capability, and each one adds a way to go wrong.

It acts

An agent produces actions: a search, a calendar entry, an email, a click on a web page, through tools (defined below). Once a program can act, "should this action happen?" needs an answer that does not depend only on the program's own judgement. That answer is the gate ({{ch:the-gate}}).

It remembers

A chatbot conversation starts empty. A personal agent should know, on Thursday, that you told it on Monday you do not eat meat, or that a task was left half done. That requires memory that outlives a conversation and survives a restart of the program ({{ch:memory}}). Memory is also a risk: anything saved is shown to the model again later, so a false or planted "fact" keeps doing damage.

It speaks first

A personal agent can send a reminder at nine o'clock, run a morning summary of the news, or tell you that a reply you were waiting for has arrived, without a message from you ({{ch:acting-unasked}}). Work that starts with nobody watching cannot be approved in the moment, so it must be restricted to what is safe unattended.

It holds the owner's accounts

To do errands, the agent needs the keys to your mail, your calendar and the sites you use: the most valuable access you have. Handling sign-ins and secrets is therefore a central design problem ({{ch:secrets-and-sign-ins}}).

Each property of a personal agent, what it needs, and the risk it introduces.
PropertyWhat it needsThe new risk
ActsTools the model can requestAn action nobody wanted: a sent email, a deleted file
RemembersA store that outlives the conversationA wrong or planted fact that is believed in every later conversation
Speaks firstA scheduler and something that watches for eventsWork, and spending, that happens while nobody is looking
Holds accountsConnections to the owner's services and saved sign-insEverything the owner can do, a misled program can attempt

The vocabulary of the book

The following words are used loosely elsewhere and exactly here. Later chapters rely on these meanings.

Definitions
Model
The language model: a program, usually run by a vendor and reached over the network, that takes text in and produces text out. In this book it is the part that reads, writes and chooses. It does nothing else.
Tool
One action the model may choose: search the web, list the calendar, send an email. Each tool has a name, a description and a stated shape for its inputs.
Tool call
The model's request to use a tool with particular inputs. The model does not perform the action. It writes the request; ordinary code decides whether to perform it, performs it, and hands back the result.
Step
One call to the model. A task usually takes several steps: one to ask for a search, another to read the results and answer.
Turn
Everything that happens between one message from the owner and the agent's reply. A turn is made of one or more steps.
Owner
The one person the agent works for. Only the owner's messages are acted on; anyone else's are dropped.
Channel
The place the conversation happens, such as a private chat in Telegram or WhatsApp ({{ch:channels}}).
Connector
A set of tools that reach one outside service, such as a mail account, through that service's official interface.
Gate
Code that sits between the model's tool calls and the tools themselves. For each call it decides to allow it, to ask the owner, or to refuse it.
Routine
A task the agent runs by itself on a schedule, with nobody watching, such as a morning summary. A reminder is simpler: a fixed message sent at a set time.
Shell
The ordinary, predictable program wrapped around the model. It receives messages, runs the loop, holds the gate and keeps the log. (This has nothing to do with a command-line shell.)

The definition of a tool call matters most for safety. Because the model only asks and code acts, there is always a moment between the asking and the doing where a rule can be enforced. Most of the safety measures in later chapters live there.

The design space

The clearest way to see what a personal agent must contain is to look at products that already exist. This book measures itself against three commercial products, Instinct, Muse and Grok Bot, as they stood at the time of writing, from documentation, press and the makers' own writing, not from testing them side by side. Each claim carries a grade saying how it is known (explained under "What counts as working", below).

Three products, one design

Instinct is a personal agent you text or phone. Secondary Its channels are iMessage, WhatsApp, phone calls and an email address of its own for each user (TechCrunch). Its internals are known only from its founders and investors, with no engineering write-up to check them against.

Muse is Meta's personal agent. Secondary It sends email, books travel, fills in forms and shops with approval for each purchase (TechCrunch). Maker's claim In its maker's unaudited account of its security design, a separate program outside the agent is the only thing that can permit an action (Meta's post).

Grok Bot is xAI's agent product. Verified Its documentation describes Bots that work on a persistent cloud computer, use connected apps or a browser, ask for approval with cards, and can run a saved task on a schedule (xAI documentation).

Set side by side, the three are one design. Six elements appear in all of them:

  1. One conversation in front of everything, useful before any account is connected.
  2. A coordinating agent that hands narrower jobs to narrower workers.
  3. A persistent computer with a browser that stays signed in between tasks.
  4. Connectors first, screens second: official interfaces where they exist, operating the web page where they do not.
  5. Background work: routines and check-ins the agent starts itself.
  6. Approval before sending, paying or deleting, with the person taking over for bot checks and passkeys.

Where products of this kind have failed

The public failures teach more than the features. Secondary Instinct was reported to have sent an email without asking; to have followed instructions planted in an email it was reading; to have gone on summarising an inbox three hours after the user disconnected it; and to have taken a sign-up code out of a user's mail to finish a booking (TechCrunch). Muse was blocked by a large retailer and drew complaints about invented details and about too many approval prompts. Grok Bot's users report running out of their weekly allowance days early.

Definition
Prompt injection
Text placed where an agent will read it, such as a web page, an email or a calendar invitation, written to look like instructions. A model cannot reliably tell its owner's instructions apart from instructions inside the material it was asked to read. {{ch:untrusted-content}} treats it in full.

Sort the failures by cause and a pattern appears.

Reported failures of commercial personal agents, sorted by cause. The causes are our classification.
FailureCauseThe boundary that should have held

Obeyed instructions in an emailPrompt injection meeting a missing gateThe same gate: a fooled model can request, not perform

None of these is the model being too unintelligent for the task. Each is a boundary that should have held whatever the model decided, and did not. The design response is the principle this book rests on: the model proposes, code grants. The model may request any action; whether the action happens is decided by code the model cannot alter. {{ch:the-agent-loop}} states it in full.

OpenInstinct, an independent open-source imitation of Instinct by a different company, shows the opposite arrangement. Verified Its approvals are enforced by written instructions to the model; no code stops the send or the purchase (repository). An instruction can be argued away by a page the model reads; code cannot be.

Why this design and not the obvious alternatives

Three simpler designs suggest themselves. A chatbot that explains the steps is safe because it does nothing, and useless for the same reason. An agent told in its instructions never to send without asking (the OpenInstinct arrangement) works until the model reads something that persuades it otherwise. An agent that asks about every action is safe on paper, but an owner asked twenty times a day learns to tap Yes without reading; Muse's users complained of exactly this.

The design this book follows takes a fourth path. Reading is allowed without a question. Anything that changes the world outside the agent's own files is held by code, and the owner is shown a description built by code from the call's real inputs, not written by the model. The figure traces it for the lunch errand.

The book's system talks to its owner in Telegram first, with WhatsApp added later ({{ch:channels}}). Verified Telegram lets a bot stream a reply as it is written and attach buttons to a message, which is how an approval is answered. The cost is reach: a Telegram bot cannot message someone who has not started a chat with it, and cannot place a phone call.

Where the definition lives in the code

The boundaries that go with the four properties are each held by a few lines of code. The first is the start of the function in odysseus/conversation.py that handles every incoming message:

# 1. Who may speak. Anyone but the owner gets no reply at all.
if user_id != self._s.owner_id:
    self._journal.write("dropped", user_id=user_id)
    return

The check compares the sender's numeric id, which the channel supplies and the sender cannot choose, with the one id in the settings. A stranger gets no reply, not even a refusal, and no model is called, so a stranger cannot spend the owner's money. Without this check, anyone who learned the bot's name could use the owner's accounts.

The second is the opening of odysseus/gate.py, which states the gate's three answers:

For every tool call the gate gives one of three answers:

  allow    it happens
  ask      it is held; the owner is shown exactly what will happen and taps a
           button; it happens only on "Approve"
  refuse   it does not happen

The model can request anything. It cannot grant anything.

This is "it acts" with its boundary attached. The same file refuses any tool for which no rule exists, so a tool added by mistake does not run by default.

The third is from odysseus/tools.py, and concerns speaking first:

ALLOWED_TOOLS = frozenset({SEARCH_TOOL, *MEMORY_TOOLS, *SCHEDULE_TOOLS})
ROUTINE_TOOLS = frozenset({SEARCH_TOOL, _name("recall")})

A conversation may search, use its memory and schedule things. A routine, with nobody watching, may search the web and its saved notes (and, once accounts are connected, read mail, calendar and other services, with each call checked to be a read) and write nothing.

The fourth is a sentence from the model's standing instructions in odysseus/agent.py:

If asked for one of those, say plainly that it is not built yet. Do not
pretend, and do not describe steps as done that you have not done.

A model asked for something it has no tool for may describe doing it anyway. The instruction lowers the chance and guarantees nothing, which is why the checks below never rely on what the model says it did.

Worked example: one errand, and how to score it

Take the lunch errand through the system, then ask how anyone would know it had worked.

  1. The owner writes: "Find a time next week for lunch with Sam and send him an invite." The shell checks the sender is the owner, checks today's budget is not used up, and starts a task.
  2. The model, given the message and a list of tools, requests calendar_list for next week. The gate's rule for reading the calendar is allow. Code fetches the events and returns them to the model.
  3. The model finds Wednesday 12:30 free and requests calendar_create with Sam as a guest. Creating an event with guests emails them, so the gate's rule is ask. The gate builds the question from the inputs and posts it in the chat with Approve and Decline buttons. The task waits.
  4. The owner taps Approve. Code creates the event with exactly the inputs that were shown and returns the result. The model writes: "Done: lunch with Sam, Wednesday 12:30 to 13:30, invitation sent."

The reply in step 4 is the agent's belief, not a measurement. To score the errand, something other than the agent checks the end state: is there one event on Wednesday at 12:30, is Sam its only guest, was it created only after the question was shown, and was nothing else changed?

Now score a small invented suite of 20 errands. Checked afterwards, 17 reached the right end state, but in 3 of those the agent sent something without the question being shown. Task completion is 17 of 20 (85%); trusted completion is 14 of 20 (70%). Both terms are defined in the next section.

What counts as working

An agent that finishes a task says so. An agent that fails a task quite often says so too, in the same confident words. The model's own report is therefore not a measurement.

Definitions
Task completion
The share of tasks whose outcome is correct when checked by something other than the agent: a person, a second program, or the state of the account afterwards.
Trusted completion
The share of tasks that were completed and in which the agent stayed inside the owner's rules: it asked where it should have asked, touched nothing it was not meant to, and leaked nothing.

Trusted completion, the stricter of the two, is the measure this book uses. The reported failures above are almost all failures of its second part.

Things someone measured, things a company said about itself, and things that merely sound right look alike on the page. Every claim in this book therefore carries one of four grades.

How high is the bar?

One public test of commercial assistants exists. A company called micro1 gave 20 tasks to six assistants and had experts mark each attempt. Secondary Read as trusted completion, the results were 65% for Instinct and for Grok Bot, 55% for Muse, and 80% for the best assistant tested. The authors describe the sample as small and the ranking as not definitive, and accounts of the results disagree about which assistants were tested. With 20 tasks, two tasks are ten percentage points, so the figures indicate the bar roughly; they are not a target.

What a first system leaves out

The book's system deliberately leaves out things the reference products do:

  • Payments. A wrong payment is the hardest action to undo, and it needs card handling that is a security problem of its own.
  • Phone calls. A call speaks for the owner in real time, where no approval question can be put between a sentence and the person hearing it.
  • Group chats. Other people's messages arrive beside the owner's, and "act only on the owner" becomes much harder to keep.
  • Speaking to third parties, inside the owner's conversations or to other people's agents, where the owner has not read the words first.

Each of these adds a way to cause harm that the simpler system does not have. Each can be added to a working system later. None of them can make a broken system work. The rule is to wait until the simpler system has a stable, independently checked score. {{ch:the-agent-loop}} describes the minimal core everything else is built on.

What goes wrong

Believing the agent's report. Counting a task as done because the agent said so. Every check must look at the world (the calendar, the sent mail, the gate's log), never at the reply.

Believing a test the builder wrote. A check written by the same person who wrote the code shares that person's assumptions. The evaluation in {{ch:testing-and-evaluation}} found that an agent that does nothing at all and replies with nothing scored 8 out of 40 on the first version of its checks. Verified After the checks were tightened (a reply is required; a declined send must first have reached the approval question) the do-nothing agent scores 0, and that run is repeated whenever errands are added.

The same holds for tests with a stand-in. {{ch:the-agent-loop}} tells how a full set of passing tests hid a wrong belief about how the model library reports cost, a belief that only a run against the real library revealed.

Forgetting the cost. A system for one person escapes the problem of scale but should still count its own spending from the first day, and stop when a limit is reached ({{ch:cost}}).

How to test it

A test of a personal agent must check behaviour at the boundaries, not the quality of its prose:

  • A message from anyone but the owner produces no reply and no model call.
  • A tool not on the list of permitted tools is refused by code, whatever the model asks.
  • An action with consequences reaches the owner as a question before it happens, and does not happen when declined.
  • An agent that does nothing scores zero.
  • The outcome of each errand is read from the state of the world afterwards, not from the reply.

The repository's tests cover the first three. tests/test_slice.py (28 tests, all passing) checks that a stranger's message gets no reply and no model call, and that the tool policy refuses a shell command, a file write, a mail send and a web fetch. tests/test_gate.py and tests/test_apps.py check that a send is held until the owner taps Approve, that it does not happen when declined, and that a planted instruction cannot cause a send without a tap. These tests use stand-ins for the model and the mail service, so they show the code does what its authors intended, no more.

The last two need an evaluation against tasks. An errand suite has been run ({{ch:testing-and-evaluation}}, {{ch:a-second-reading}}): Verified in its latest run, one run of the suite, 563 of 581 runs passed, against a stand-in mail and calendar, with errands and checks written by the builders. That is weak evidence of competence and is not comparable with the micro1 figures, which come from real accounts.

What is proven and what is not

Verified The owner check, the refusal of unlisted tools and the routine's read-only tool set exist in the code and are covered by passing tests. The holding of a send until the owner approves is covered by passing tests with stand-ins. An errand suite in a stand-in world passed 563 of 581 runs in its latest run, and an agent that does nothing scores zero on it.

Secondary What is said here about the three commercial products' behaviour and failures comes from press and documentation, not from our own use of them.

Not tested No trusted-completion score exists for the book's system on its owner's real accounts and real errands. Until one does, no sentence in this book says the system is as good as, or better than, any product it is compared with.

Summary
  • A personal agent differs from a chatbot in four ways: it acts, it remembers, it speaks first and it holds its owner's accounts. Each adds a capability and a risk.
  • The model only requests actions; code performs them. That gap is where most safety measures live.
  • Commercial personal agents share six elements: one conversation, a coordinating agent, a persistent signed-in computer, connectors before screens, background work, and approval.
  • Their reported failures are of boundaries and cost, not model ability: hence "the model proposes, code grants".
  • A result counts only when something other than the agent checked it. Trusted completion counts tasks that were done and done within the owner's rules.
  • A first system leaves out payments, calls, group chats and speaking to third parties, because each adds harm and none fixes what is broken.
