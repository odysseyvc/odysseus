After this chapter you should be able to
  • Work out roughly what a model call costs from its token counts and a price table, and explain why a long conversation makes every later call dearer.
  • List every kind of paid call an agent makes, and say for each whether the vendor reports its price or the program has to estimate it.
  • Build a ledger that is derived from the journal by one function, so that the money spent cannot drift from the record of what was done.
  • Explain how a per-task budget and a per-day budget stop work, and where each falls short.
  • Recognise a design that pays for the same input many times, and move that work into a separate run that is paid for once.
  • Read a table of measured costs critically: what each figure measured, how many times, and what it leaves out.

The problem: money that moves without anyone noticing

An agent spends money every time it calls a model, searches the web, opens a browser or reads from a paid service. Nobody sees an invoice per message. If the program does not count, the first sign of a fault is the monthly bill.

The case this chapter is built around: the owner sends a fourteen-page pitch deck, as a PDF, into the chat. In the design first built, so that the model could see the charts and logos that text recognition drops ({{ch:files-pictures-and-voice}}), the PDF was placed in the conversation itself. The reply cost 12 cents. Later in the same long-running conversation the deck was sent again, and then a third time. The third sending cost 34 cents. Verified, one sending each. The deck was the same each time; the conversation before it was longer.

Explaining that number needs four ideas: what a model call is billed for, why a conversation's length dominates, which other services charge and how their price is learnt, and how a ledger and budgets turn prices into a decision to stop.

The concepts

Definition
Token
The unit in which a model reads and writes text, roughly a word or part of one. Vendors bill per million tokens read (input) and, at a higher price, written (output). A PDF page shown as a picture also becomes tokens.
Definition
Context
Everything the model is shown in one call: instructions, the conversation so far, tool results, files and the new message. A model keeps nothing between calls, so the context is sent, and billed as input, every time.
Definition
Prompt cache
A vendor feature that stores the start of a context sent repeatedly, so that later calls beginning with the same text pay much less to read it. Writing to the cache costs a little more than ordinary input. (A general description; the program's figures are in the price table below.)
Definition
Metered service
An outside service that charges per use: per search, per browser run, per page recognised, per minute transcribed, per item returned. A flat subscription is not metered.
Definition
Ledger
The program's running account of money spent per calendar day. Here it is not stored: it is computed from the journal (the append-only record of every step, introduced in {{ch:the-conversation}}).
Definition
Budget
A limit that changes what the program does when spending reaches it: a task is ended, or not started. A figure that is only displayed is not a budget.

Why the conversation's length dominates

A task is several model calls ({{ch:the-agent-loop}}), and each call sends the whole context. The input billed for a task is therefore roughly the context's size times the number of calls, and the context includes every earlier message.

Output is dearer per token but small. Input is cheaper per token but large and growing, and in a conversation kept for weeks ({{ch:staying-up}}) it wins. Anything placed in the conversation is paid for again by every later call until the library condenses the conversation or the owner sends /new.

The price table the program uses is in odysseus/agent.py:

# Dollars per million tokens: input, output, cache read, cache write.
# Used only to end a task early; the recorded cost is the SDK's own figure.
# All four were checked against the maker's price list (cache writes are the five-minute rate); prices change.
# Not in the table: the small model costs five times as much on a prompt over 100,000 tokens, so an estimate
# for such a prompt on that model is too low. No prompt this program builds for it comes near that size.
PRICES = {
    "claude-sonnet-5-5": (2.00, 10.00, 0.10, 2.50),
    "claude-opus-5-5": (4.00, 20.00, 0.20, 5.00),
    "claude-haiku-5-5": (0.10, 0.50, 0.01, 0.125),
}
DEAREST = max(PRICES.values())   # used for a model not in the table, so the estimate errs high

A cache read is priced at a twentieth of ordinary input for the two larger models and a tenth for the small one. Caching softens the cost of a long context; it does not remove it, since on the main model twenty cached readings cost as much as one uncached. The comment also says where the figures came from and what the table leaves out. The cache-write figures were once an assumption (1.25 times input) and were later checked against the price list, which also offers a one-hour cache at twice the input price: an alternative to beginning a new conversation after a pause that has not been tried.

Illustration: arithmetic, not a measurement

Suppose, for the arithmetic only, that a PDF page shown to the model costs two to three thousand tokens (an assumed figure: the program has never measured it). Then fourteen pages are about 28,000 to 42,000. At $2 per million that is about 6 to 8 cents per model call uncached, or 0.3 to 0.4 cents read from a cache. A task of three calls in a conversation holding three copies of the deck pays for nine readings of fourteen pages. This shows the shape of the problem, not how the 34 cents was made up: the split between cached and uncached tokens was not measured.

The design

Every paid call leaves a line, and one function prices the line

Each way of spending money writes a journal line when it happens. One function, cost_of, returns what a line cost, and the ledger is that function applied to every line. Nothing else adds to it.

Reported, estimated, or not counted

Some vendors return a price with every answer; for the rest the program estimates.

Budgets: three limits, and why the program counts for itself

{{ch:the-conversation}} introduced the three limits: 25 steps and $0.50 per task, $3.00 per day. The day's limit is read from the ledger before a task starts, so a refused task costs nothing. The per-task limits are checked as each model call arrives, and cannot use the library's figure, which comes only at the end of a run and as a running total. So the program estimates as it goes, uses the estimate only to decide when to stop, and records the library's figure afterwards.

Unattended work has a fourth kind of limit: with no owner to ask, a routine may make only a fixed number of reads of a paid service per run (eight for X, in odysseus/mcpapp.py). And an incoming event that no watch covers calls no model at all.

The mechanism

The one definition

The whole ledger rests on this function in odysseus/journal.py:

OCR_USD_PER_PAGE = 0.002
VOICE_USD_PER_MINUTE = 0.003


def cost_of(rec: dict[str, Any]) -> float:
    ...
    kind = rec.get("kind")
    try:
        if kind in ("task_end", "event"):
            return float(rec.get("cost_usd") or 0.0)
        if kind == "tool" and rec.get("name") != "browse":      # a web search at the price the service reported; a paid read of a
            return float(rec.get("cost_usd") or 0.0)             # connected service, as estimated. A browser run is in its task_end.
        if kind == "file" and rec.get("ok") and rec.get("pages"):
            return float(rec["pages"]) * OCR_USD_PER_PAGE
        if kind == "voice" and rec.get("ok"):
            return float(rec.get("seconds") or 0) / 60 * VOICE_USD_PER_MINUTE
    except (TypeError, ValueError):
        pass
    return 0.0

(The docstring, omitted, lists the same cases in words.) Every kind not named returns zero, so a new kind of line is not counted by accident. A malformed number returns zero instead of crashing start-up. And there is exactly one place to look when asking "is this counted?".

The ledger applies it:

        self._by_day: dict[str, float] = {}
        for rec in journal.read():
            self._count(rec)
        journal.listeners.append(self._count)

    def _count(self, rec: dict[str, Any]) -> None:
        usd = cost_of(rec)
        if usd:
            day = datetime.fromtimestamp(rec["ts"], self._zone).date().isoformat()
            self._by_day[day] = self._by_day.get(day, 0.0) + usd

At start-up it reads the whole journal, then listens for new lines; the same function sees every line both times, so the figure survives a restart. The day is computed in the owner's time zone, from a setting. Without that, a server elsewhere would reset the owner's budget in the middle of their afternoon.

From a running total to a task's cost

The library reports a running total for the conversation. The cost of one task is the difference (odysseus/agent.py):

        total = float(result.total_cost_usd or 0.0)
        continued = bool(result.session_id) and result.session_id == self.session_id
        cost = max(0.0, total - self._session_cost) if continued else total
        if result.session_id and result.session_id != self.session_id:
            self.session_id = result.session_id
            self._save_session()
        self._session_cost = max(total, self._session_cost) if continued else total

In the same conversation, the task's cost is the new total minus the last one seen; in a new one, the whole total. The max calls guard against a total that goes backwards. Without this, summing running totals overstates spending more as the conversation grows.

Estimating during the task

def estimate_usd(model: str, usage: dict[str, Any]) -> float:
    p_in, p_out, p_read, p_write = PRICES.get(model, DEAREST)
    return (
        (usage.get("input_tokens") or 0) * p_in
        + (usage.get("output_tokens") or 0) * p_out
        + (usage.get("cache_read_input_tokens") or 0) * p_read
        + (usage.get("cache_creation_input_tokens") or 0) * p_write
    ) / 1_000_000

Each model call reports four kinds of token count, each with its price. A model not in the table gets the dearest row, so a new model ends tasks early rather than late: an unfinished task is the cheaper mistake. The test test_cost_estimate_from_token_counts checks one case by hand: a million input tokens, a hundred thousand output tokens and a million cache-read tokens on the main model cost $2.00 + $1.00 + $0.10.

Estimating a service that does not report its price

X's server does not say what a call cost. The program estimates from what came back (odysseus/mcpapp.py):

def estimate(spec: dict[str, Any], name: str, text: str) -> float:
    """What one read probably cost, from how many items came back. Zero for a service that does not charge by the item."""
    price = spec.get("price")
    if not price or name in price.get("free", ()):
        return 0.0
    try:
        data = json.loads(text).get("data")
    except (ValueError, AttributeError):
        return 0.0
    items = len(data) if isinstance(data, list) else (1 if data else 0)
    each = price["default"]
    for key in ("own", "people"):
        rate, marks = price.get(key, (None, ()))
        if rate is not None and any(m in name for m in marks):
            each = rate
            break
    return round(items * each, 4)

The service's entry prices an item at $0.005 by default (a post), $0.010 for a profile, $0.001 for the owner's own data, and nothing for the credit check; its comment reads "An estimate: the bill is X's, not this table's." The figure goes to the journal with estimated=True, so a reported price can always be told from a guessed one. The model is also told the prices in words and asked to request small pages of twenty to fifty items: a cost control too, though one the model may or may not follow.

A second runner is built with no tools at all, and forget_session throws its conversation away before and after each file. Its notes, at most 9,000 characters of text, are what the owner's conversation receives ({{ch:decks-and-data-rooms}} covers their content). A run that fails or times out is still costed from the running estimate: a failure is not free on the bill, so it is not free in the ledger.

Worked examples

The deck, before and after

Step by step, after the repair, for the real fourteen-page deck in a conversation started afresh:

  1. The owner sends the PDF with no message. The control layer checks the sender, then sends the file to text recognition, which returns the text with each page numbered. The journal gets a file line with pages: 14; cost_of prices it at 14 × $0.002 = 2.8 cents by the fixed estimate (a figure computed by the program, and not part of the measured 20 cents below).
  2. The file is a PDF of at most 25 pages and 12 MB, and the day's budget has room, so the page reader runs. It sees the PDF and the text, and writes notes such as the two figures on a benchmark chart where the company's model is behind. It is thrown away. The journal gets a tool line named see_pages. Verified: 8 cents.
  3. The conversation receives the file's text and the reader's notes as one block of text inside the owner's message, and the model writes its take. Verified: 12 cents for the conversation, 20 cents in all.
  4. Every later message in the conversation carries that block of text, but not the fourteen page images.

Two things were given up: the conversation's model no longer sees a page, so later questions about a chart are answered from the notes; and a second model now stands between page and reader, one more place for a mistake. One thing was gained besides money: a reader with no tools can at worst describe a page wrongly, whatever the page says to it ({{ch:untrusted-content}}).

The reader's model is a setting. On an invented eleven-page deck the small model cost a third of a cent and the main model five and a half cents, and both reported the same chart and planted line. Verified, one run each. The main model stays the default, because one drawn chart is no basis for trusting the small one with real slides.

Design decisions driven by cost

  • A cheaper model for unattended work. Scheduled routines run on a background model, claude-haiku-5-5 by default in odysseus/config.py, priced in the table at a twentieth of the main model. A routine has a narrow job, nobody watching, and runs whether or not it finds anything; measured runs cost about $0.0015 ({{ch:acting-unasked}}). Work whose judgement the owner will act on (a meeting brief, the page reader) uses the main model.
  • Code instead of a model. A reminder is sent by code and costs nothing; an email no watch covers is dropped by code; commands are answered by code.
  • Refusals before any model call. A stranger's message, a task when the day's budget is spent, and the page reader for a file that is too long or arrives when the budget is spent are all refused before any model call.
  • A conversation that begins again after a pause. The price of a message is, roughly, the size of the whole conversation behind it. The cache softens that only while messages follow one another within a few minutes; after a longer gap the whole conversation is written to the cache again, at more than the ordinary input price. A personal assistant is mostly used in exactly that way: a message, then nothing for an hour. So code, not the model, decides when to begin a new conversation: after two hours without a message, or after ten idle minutes once the last call sent the model more than 40,000 tokens. The new conversation is given the last three exchanges in words, cut where long, and the saved memory. A file's text is not carried: its first line stands for it. A web search's results, which stay in the conversation for as long as it lasts, are cut to 12,000 characters. The mechanism is in {{ch:the-conversation}}. Closing the old conversation with a summary costs about two hundredths of a cent on the small model ({{ch:memory}}), against several cents for every later message that would otherwise have carried the whole of it.
  • Look only where there is something to see. A long PDF's pages are not all shown to the page reader. Code picks the pages with pictures from what text recognition already returned, and only those are looked at: six pages of an invented forty-five-page deck, for three cents ({{ch:files-pictures-and-voice}}).
  • The cheapest model that does the job, shown by measurement. The second reader of outgoing actions was tried on the small model and the main one. Both caught every planted fault with no false alarm; the small one costs a twentieth as much, so it is used ({{ch:the-gate}}).
  • The cheapest route that reaches the information. For a morning digest of posts, X's interface would cost about 15 cents a morning (worked out from its published prices, not measured), web search under a cent a search, and a hosted browser 4 to 8 cents a run. Web search became the fallback when X refuses, being cheaper and able to run unattended ({{ch:sourcing}}).

What goes wrong

A total read as a cost

Case note

The first version added the library's reported cost to the day after each task. Three trivial questions reported $0.0013, $0.0026 and $0.0029, and the ledger recorded $0.0068 for work that cost $0.0029, because the figure was a running total for the conversation. The tests had passed, because the stand-in for the library reported costs the way the authors believed the library did. The first live run found it.

Before summing a number, find out what it is a number of: a call, a run, a session or a billing period.

A ledger that left things out

A later reading of the whole program ({{ch:a-second-reading}}) found that the ledger counted model calls and browser runs and nothing else. Searches, files and voice notes were not counted. Checks of incoming events were counted until the next restart and then forgotten. A forced stop cost nothing. "Today" ended at the machine's midnight. One move fixed all of these: one pricing function over every line.

A wider rule that counted one thing twice

Case note

The ledger at first priced one kind of tool line, web search. Making it price "any tool line that reports a cost" was a one-line change, made so that paid reads of X would count. It doubled the cost of every browser run, because a browser run's cost is already added to the task_end of the task it belongs to. An existing browser test failed, reading 0.07 where it expected 0.04. The rule now names its one exception, and a test asserts that a browse line is priced at zero.

A derived ledger moves the risk from forgetting to count to counting twice. The defence is a test for each case that must not be counted, beside those that must.

Budgets that are thresholds, not ceilings

The day's budget is checked before a task starts, so a task that begins a cent under the limit can still spend its full $0.50. The agent library's own hard cap is not set. The per-task limit rests on an estimate that leaves out the small model's higher price for very long prompts, and it acts only after the call that crossed it has been paid for. These are known and not repaired.

Costs nobody reconciled

Every figure here is what a service said or what the program estimated. The code itself says the per-page and per-minute prices "should be checked against an invoice". X's estimate has never met a read that returned posts. Whether the running total continues correctly after a conversation is resumed from disk has not been measured.

How to test it

A test of cost handling must check that each paid kind of line is priced and each that must not be (a browser line, a scheduling record) is priced at zero; that the ledger after a restart equals the ledger before it; that a day ends at the owner's midnight; that a task's cost is a difference of running totals; that each budget ends or refuses work, the daily one with no model call; that an estimate errs high for an unknown model; and that a separate run writes its own cost line.

The existing tests do these with stand-ins. Verified, unit tests: the nine-line ledger above and its equality after a restart, and the owner's midnight (tests/test_stage0.py); a search's reported price reaching the ledger (same file); running-total differences, the token estimate, both per-task limits and the daily refusal (tests/test_slice.py); X's estimate by item type, and a browser line priced at zero (tests/test_mcpapp.py); a browser run's cost added to its task (tests/test_browser.py); the page reader shown the file, given no tools, and its cost counted (tests/test_ocr.py).

Verified, unit tests (tests/test_fresh.py): half an hour's pause continues the same conversation and three hours' begins a new one that carries the last exchanges and the memory; a large conversation begins again after fifteen idle minutes and not after four, and a small one does not; a file's text is left out of what is carried; the rule can be switched off; a search's results are cut.

What none of them can show is whether the prices are right. A test can prove that the ledger adds what the journal says. Only an invoice can prove that the journal says what was charged.

What is proven and what is not

Verified by unit tests: the ledger's single definition and everything listed above. Verified live, once each: the deck's 12 and 34 cents in a long conversation, and 20 cents with the separate reader in a fresh one; the reader's cost on each of two models; and the other single runs in the table of measured costs.

Not tested: whether the cost of a conversation stays flat across several decks with the separate reader, which is the claim the design rests on; any reconciliation of the ledger with a vendor's invoice; X's per-item estimate against a read that returned items; what a message costs before and after the rule that begins a new conversation after a pause, and whether the three exchanges it carries are enough for the owner not to notice; whether costs are counted correctly across a resumed conversation. The daily budget's value was a guess and remains one.

Summary
  • A model call is billed by tokens in and out. Every call re-sends the whole context, so in a long conversation the input side dominates, and anything placed in the conversation is paid for again by every later call.
  • Caching cuts the price of re-reading a context to between a tenth and a twentieth in the program's table. It softens the cost of a long conversation; it does not remove it.
  • Every paid call writes a journal line. One function, cost_of, prices a line; the ledger is that function summed per owner's day. The figure cannot drift from the record.
  • Some prices are reported by the vendor, some estimated by the program, and the journal marks which. None has been checked against an invoice. Cost also drives design: a cheaper model for unattended work, code before models, refusing before spending.
  • Budgets stop work: per task as model calls arrive, per day before a task starts. The daily one is a threshold, not a hard ceiling.
  • A PDF kept in the conversation cost 34 cents on its third sending against 12 on its first. Reading its pages once, in a throwaway run with no tools, and passing on only text, is the fix; its long-run saving is not measured.
Exercises
  1. Using the price table, work out the estimated cost of a model call that reports 40,000 input tokens, 600 output tokens and no cached tokens on the main model. Then work it out again with 38,000 of those input tokens read from the cache. What fraction of the first figure is the second?
  2. Why does cost_of price a browse line at zero but a see_pages line at its full cost, when both are separate runs of another model or service? What would go wrong if the page reader's cost were added to the conversation task's task_end instead?
