What the slice does

Stage 1 of the plan in Chapter 5 asks for a conversation that runs from one end to the other and does very little. The slice does five things:

  1. It receives messages from Telegram and answers only its owner.
  2. It runs an agent loop whose single tool is a web search.
  3. It shows the reply as it is being written.
  4. It stops when told to, whether or not the model cooperates.
  5. It counts what each task costs, ends a task that costs too much, and writes every step to a log.

As first built it had no memory between conversations, no schedule, no mail and no browser, and its instructions told the model so, in order that it says "that is not built yet" when asked, and does not pretend. Memory has since been added and is the subject of Chapter 7; this chapter describes the slice without it.

The right-hand column is the point of the arrangement. Only one file hands anything to the model, and the rules live in a file that does not. In the terms of Chapter 3, conversation.py and the limits in agent.py are the shell; the model is a guest inside it.

Keeping the rules apart from Telegram has a second benefit. The tests exercise conversation.py directly with a pretend chat, so they run in seconds and need no network.

Who may speak

The first lines of the function that handles every incoming message are these:

async def handle(self, user_id: int, text: str, chat: Chat) -> None:
    # 1. Who may speak. Anyone but the owner gets no reply at all.
    if user_id != self._s.owner_id:
        self._journal.write("dropped", user_id=user_id)
        return

A Telegram bot can be found and messaged by anyone who learns its name. The check compares the sender's numeric ID, which Telegram supplies and the sender cannot choose, against the one ID in the settings.

A stranger receives nothing, not even a refusal. A reply of any kind confirms that the bot is alive and gives a prober something to work with. The message is recorded in the log and dropped before any model is called, so a stranger also cannot cost the owner money.

The wiring in telegram.py adds one more restriction: it listens in private chats only. A bot added to a group would otherwise be handed other people's messages.

The loop, and what the model is allowed to touch

The agent loop comes from a library, the Claude Agent SDK. The bot connects to it once, when it starts, and keeps that connection for every message. The first version connected afresh for each message, and a one-word reply took 8 to 17 seconds; with one connection kept open it takes about 2 (build log entry 008). Verified

The library was built for programming assistants and arrives with tools for running commands and editing files. A personal assistant on a server should have none of those, so the options passed to the library remove them:

ClaudeAgentOptions(
    model=self._s.model,
    system_prompt=SYSTEM_PROMPT,
    tools=[],                          # none of the SDK's built-in tools
    mcp_servers={SERVER: self._server},
    strict_mcp_config=True,            # ignore tool servers configured on the machine
    allowed_tools=sorted(ALLOWED_TOOLS),
    can_use_tool=tool_policy,          # anything not listed is refused by code
    setting_sources=[],                # ignore settings files on the machine
    ...
)

Three lines do the restricting. tools=[] asks for no built-in tools. allowed_tools lists the one tool that may run without a question, the search. can_use_tool names a function that the library consults about anything else:

ALLOWED_TOOLS = frozenset({SEARCH_TOOL})

async def tool_policy(tool_name, tool_input, context):
    if tool_name in ALLOWED_TOOLS:
        return PermissionResultAllow()
    return PermissionResultDeny(
        message=f"{tool_name} is not available in this version of Odysseus.")

This is the gate of Chapter 3 in its smallest form. It has two of its three answers, allow and refuse. The third, ask the person, arrives at stage 4, when there is first something worth asking about.

Belt and braces, and an honest gap

The removal of built-in tools and the refusing function overlap on purpose: if one fails, the other still holds. When this chapter was first written, whether tools=[] removes every built-in tool had been checked only by reading the library's documentation, which did not state it outright. Verified The first live run settled it: the library's own start-up report listed exactly one tool, the search.

Stop, in two layers

Chapter 3 said that stopping must work when the model is behaving badly, since that is when it is needed. The slice therefore treats "stop" as a command to the shell. The word is matched in conversation.py and is never passed to the model.

Layer one asks the library to interrupt the run. In the ordinary case the run ends at once and reports what it had spent.

Layer two exists for the case where layer one is ignored, whether through a fault in the library, a stalled network call or anything else. The shell waits a short grace period and then cancels the task itself:

done, _ = await asyncio.wait({task}, timeout=self._s.stop_grace_s)
if not done:
    task.cancel()
    await asyncio.gather(task, return_exceptions=True)
    self._journal.write("task_end", status="stopped", forced=True, cost_usd=0.0)
    await chat.send("Stopped.")

One of the tests builds a stand-in model that never stops, sends "stop", and requires an answer within two seconds. It passes, and the log shows forced: true. A connection that had to be cancelled this way is thrown away, and the next message starts a new one that resumes the same conversation.

Verified In the live runs, layer one ended a real task in 1.1 seconds with a connection per message and in 0.13 seconds with the connection kept open, and the same connection answered the next message. Layer two has never been needed live.

A stopped task is recorded as costing nothing, because the library's running total has not yet moved. In the live run the amount appeared against the next task instead. The day's total is right; the attribution is off by one task.

While a task is running, any other message gets the reply "Still working on the last task. Send stop to end it." The slice does one thing at a time. That is a simplification, not a principle, and later stages will relax it.

Three limits on spending

The limits in the first slice, with their default values.
LimitDefaultEnforced byWhat the owner sees
Steps in one task25Our own code, counting model calls as they arrive"I ended this task because it reached its limit of 25 steps."
Money in one task$0.50Our own code, estimating cost from the tokens each call reports"I ended this task because it reached its budget of $0.50."
Money in one day$3.00Our own ledger, before any model call"Today's budget of $3.00 is used up, so I have not started this."

The library has limits of its own for steps and money, and the first version used them. They are fixed when a connection is made and count everything on that connection, so on a connection kept open all day they cannot mean "per task". The slice counts for itself instead. Steps are counted as each model call arrives. Money is estimated during the task from the token counts each call reports and the model's list prices, and the task is interrupted when the estimate reaches the limit. The amount written to the ledger afterwards is the library's own figure, not the estimate.

The daily limit is checked before the task starts, so a task refused for that reason costs nothing. The two per-task limits end a task part-way, and whatever the model had written by then is delivered with the explanation attached, so partial work is not thrown away.

In every case the owner is told what happened and why. A task that ends early and says nothing is indistinguishable from one that is still running.

The defaults are guesses. Nobody has published what a task of this kind costs, which is one of the open questions from Chapter 4, and the first week of real use is meant to replace the guesses with measurements. Verified The first measurements, one sample each: a question that needed one search cost $0.0145, and a trivial follow-up about a tenth of a cent.

Worked example: a limit that was not what it seemed

The library reports a cost at the end of each task. The first version of this code took that number to be the cost of the task and added it to the day's total.

The first live run showed otherwise. Three trivial questions in one continued conversation reported $0.0013, $0.0026 and $0.0029. The number is a running total for the conversation. Adding running totals together gives $0.0068 for work that cost $0.0029.

The same misreading affected the limit. "At most $0.50 for this task" had been passed to the library as 0.50, and the library compared it with the running total. After fifty cents of conversation, every new task would have been ended immediately.

The corrected code keeps the last total it saw, and the cost of a task is the new total minus the old one. The limit was first repaired by handing the library "the old total plus $0.50", and then, when the connection became long-lived, replaced by the count described above. All the tests had passed with the error in place, because the stand-in had been written to report costs the way we wrongly believed the library did.

The log

Every step appends one line to a file, in a format a program can read back:

{"ts": 1794860000.1, "kind": "task_start", "chars": 31}
{"ts": 1794860001.4, "kind": "tool_request", "name": "mcp__odysseus__web_search", "input": {"query": "..."}}
{"ts": 1794860002.0, "kind": "tool", "name": "web_search", "query": "...", "ok": true, "results": 5}
{"ts": 1794860004.9, "kind": "task_end", "status": "done", "cost_usd": 0.012, "turns": 2, "seconds": 4.8}

The ledger of daily spending is not stored separately. It is rebuilt from these lines when the program starts. Two records of the same fact can disagree; one record cannot. If the ledger is ever doubted, the log it was computed from is there to check.

The log holds what was asked of each tool and how each task ended. It does not hold keys, and in this slice it does not hold the text of the owner's messages, only their length.

Search results are reading matter

The search service publishes guidance for giving its search to a model as a tool, and the slice follows it. The model supplies two things for each search: a query describing the page it hopes to find, and an objective saying what the search is for, which results should come first and what to pull from them. Both are passed to the service unchanged. The request otherwise uses the service's defaults, and the model's instructions carry the service's recommended sentence about when to search, so that it looks things up instead of answering from memory that may be out of date.

The search tool returns titles, addresses and short extracts from public pages. Any of those pages may contain text written to be mistaken for instructions, which Chapter 2 defined as prompt injection. The slice does two things about it, neither of which is a cure.

First, every set of results is handed to the model beneath a fixed line stating that what follows is material to read and not an instruction from the owner. The model's standing instructions say the same. This lowers the odds of the model being misled and guarantees nothing.

Second, and this is what actually protects the owner, there is nothing for a misled model to do. The slice has no tool that sends, pays, deletes or shares. The worst outcome of a successful injection today is a wrong or strange reply. That will stop being true at stage 4, which is why the gate is built before the tools that need it.

What is tested, and what is not

The slice has 26 automated tests, which run in well under a minute. They fall into six groups.

Stop5Stop ends a running task and the connection lives on; stop works when the stand-in ignores it, and the connection is then replaced and the conversation resumed; stop with nothing running says so; a second message does not start a second task.

Compare this with the test Chapter 5 set for stage 1: a stranger gets no answer; stop ends a task even when the model is mid-reply; a task over budget ends and says so. All three are met, with one qualification that matters.

Definition
Stand-in (also called a fake)
A small piece of test code that takes the place of a real component and behaves in a fixed, scripted way. Here the stand-in replaces the model and the library that runs it.

A stand-in makes tests fast, free and repeatable, and lets them create situations that are hard to produce on demand, such as a model that never stops. Its weakness is that it behaves as we believed the real thing behaves when we wrote it. If the real library reports a stopped run differently from our script, the tests will pass and the program will be wrong.

That paragraph was written before the first live run, with a list of six points the tests could not settle. The run has now happened once, and the list is kept here with what was found.

The run also found something nobody had listed: replying with a single word took 8 to 17 seconds, nearly all of it start-up, because the loop was started afresh for every message. A list of known unknowns does not contain the unknown ones. Keeping one connection open brought this down to about 2 seconds (Section 6.4).

Summary
  • The slice is six small files. One talks to the model; the rules live in another that does not.
  • Strangers are dropped silently before any model call.
  • The model is offered one tool. Everything else is removed and, separately, refused.
  • Stop has two layers: a request to end, then cancellation after a grace period.
  • Three limits bound spending, all enforced by the slice's own code, and the owner is always told when one ends a task.
  • All 26 tests pass against a stand-in. Live runs confirmed three assumptions, overturned one about cost, and revealed slow start-up, which keeping one connection open has fixed.
Check your understanding
  1. Why does the bot send a stranger nothing, when a polite "this bot is private" would be friendlier?
    Answer

    Any reply confirms the bot exists and responds, and invites further attempts. Silence gives a prober nothing. Dropping the message before a model call also means strangers cannot spend the owner's money.

  2. The test for layer two of stop uses a stand-in that never stops. Could the same test be written against a real model?
    Answer

    Not reliably. A real model nearly always stops when interrupted, so the failure would have to be waited for. A stand-in can produce the rare case every time, which is the main reason to use one.

  3. All 21 tests pass. Give one way the program could still fail on its first live message.
    Answer

    Any place where the stand-in's script differs from the real library: for example, if the real library signals an interrupted run in a form the code does not recognise, or if it still offers a built-in tool despite the empty list. Passing tests show the code agrees with our assumptions, not that the assumptions are right.

  4. The ledger is rebuilt from the log at start-up. What would be lost by storing the day's total in its own file as well?
    Answer

    Nothing would be lost, but a second copy can drift from the first after a crash between the two writes, and then it is unclear which to believe. One record, with the total derived from it, cannot disagree with itself.
