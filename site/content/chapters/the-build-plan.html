Build in thin slices

Definition
Thin slice
The smallest version of a system that runs from one end to the other. It does very little, but every part that will exist later is present in some simple form, so that problems between the parts show up early.

The alternative to slices is to build each part fully and join them at the end. That postpones the hardest discoveries, which are almost always found at the joins: a scheduler that runs a job but cannot deliver its result to the chat, or a stop command that the browser worker never hears. One builder's account in the research describes scheduled jobs that ran correctly for a week and delivered nothing, and looked exactly like "nothing to report" (write-up). Secondary

Why this order

Stop, budget and log come first. They are dull and they are the means by which every later stage is observed and halted. An agent that cannot be stopped should not be given anything worth stopping it from.

Memory and scheduling come before any account is connected. They are low in risk, because they touch nothing outside the system, and they already distinguish an agent from a chatbot: it remembers, and it speaks first.

The gate is built before the first tool that needs it. If mail were connected first and the gate added afterwards, there would be a period in which the model could send mail unchecked. Built in the other order, that period never exists.

The browser comes last among the capabilities. It is the largest piece and the most exposed, since a browser reads whatever any web page chooses to show it. By stage 5 the gate, the budget and the stop have been in use for some time.

Measurement is stage 6 on the diagram but begins earlier. Each stage's test in the table is a small measurement. Stage 6 is where those become a standing set that is run again after every change of model or instructions.

What the build needs from its owner

Some steps cannot be done by code or by an AI agent, and should not be. Creating the Telegram bot, opening accounts with the model maker and the other vendors, and signing in to mail are done by the owner. Keys are placed in a file on the server that is never committed to the project's history and never shown to the model.

Summary
  • The build proceeds in thin slices, each running end to end.
  • The order is thread, memory, schedule, gate then mail, browser and vault, measurement.
  • Each stage has a test stated in advance. A stage is finished when its test passes, and the result goes in the build log.
Check your understanding
  1. Why is "the scheduled job ran" not a sufficient test for stage 3?
    Answer

    A job can run and fail to deliver its result. The test requires a recorded outcome for every run and an announcement of failures, so silence can only mean "nothing to say".

  2. Suppose mail reading were connected at stage 2, before the gate exists. Reading changes nothing, so what is the risk?
    Answer

    Reading mail brings untrusted text in front of the model. With no tools that change anything, the harm is limited, but any tool added before the gate, however harmless it seems, would then be reachable by planted instructions. Keeping the order strict removes the need to reason about each case.
