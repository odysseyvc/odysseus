Why it comes now

Every chapter so far has pointed here. Chapter 2 found that the reference products' public failures were boundaries that did not hold: an email sent without asking, an instruction in an inbox obeyed. Chapter 3 gave the response in five words: the model proposes, code grants. Chapter 5 put this stage before mail and calendar, so that there would never be a day on which the model could send mail unchecked.

Until now the gate has existed in a reduced form. It had two answers, allow and refuse, because nothing the agent could do was worth asking about. Chapters 7 and 8 added things that change Odysseus's own files, and handled them by allowing the change and reporting it afterwards. That is acceptable for a remembered preference. It is not acceptable for an email, which cannot be taken back. This chapter builds the third answer.

Three answers

The gate's answers
Allow
The action happens.
Ask
The action is held. The owner is shown exactly what will happen and chooses. It happens only if they approve.
Refuse
The action does not happen, and nobody is asked.

Each tool has a rule, a small piece of code that looks at the tool and its inputs and returns one of the three. A tool with no rule is refused. That default matters: when a new tool is added and somebody forgets to write its rule, it does not run, where a gate that defaulted to "allow" would have let it through.

The rules as they stand. Nothing here touches the outside world yet.
RequestAnswerWhy
Search the webAllowReads public information. Changes nothing.
Save, change or search memoryAllow, then reportWrites only to Odysseus's own files; the owner sees every change (Chapter 7).
Set a reminderAllow, then reportA fixed message to the owner at a time the owner asked for.
List or cancel scheduled jobsAllow, then reportReversible, and within Odysseus's own files.
Set up a routineAskCommits the owner to repeated unattended runs that cost money.
Anything elseRefuseNo rule exists for it.

The rule for scheduling shows that the answer can depend on the inputs and not only on the tool. Reminders and routines are set with the same tool. The rule reads the request and answers "allow" for one and "ask" for the other.

Chapter 8 allowed routines without a question and called it "a slightly bigger exception than memory was". With the gate built, that exception is withdrawn: routines are now the first thing Odysseus asks about.

The question, and who writes it

When the answer is "ask", the owner receives a message like this, with two buttons beneath it:

Set up this routine?

Every weekday, starting Wed 18 Nov 2026 at 08:00.
Each run uses the small model, can only search the web and my notes,
and sends you the result.

Instructions it will follow:
Search the web for today's biggest AI news headline. Send the owner one
short plain-text message: the headline in one line, one sentence of
context, and the source name with its URL. ...

[ Approve ]   [ Decline ]

Every word above the instructions was written by the program. The schedule line is computed from the date and the repeat setting in the request. The instructions are copied from the request itself. The model wrote the request; it did not write the question.

Chapter 1 gave the reason in an exercise, and it is the centre of this chapter. If the model wrote the question, a model that had been misled could ask "Send Priya a note about lunch?" while requesting an email to a stranger. A question assembled from the real inputs cannot say one thing while the request says another, because both are read from the same place.

For the same reason, each kind of action has its own describing code, written to put what matters where it will be read. For an email, that is the recipient on the first line. If a request cannot be described, because a field is missing or malformed, it is not shown to the owner at all and is not carried out.

Why a button and not the word "yes"

The owner answers by tapping a button. Typing "yes" does nothing. This is deliberate and it follows Muse's design from Chapter 2, in which approvals appear outside the conversation so that the answer never passes through the agent.

A typed "yes" is a message. Messages go to the model, and the model would have to decide what the "yes" was agreeing to. Anything that can put text into the conversation could then manufacture consent, and so could a model summarising the conversation to itself. A button tap goes to the program, carries only the identifier of one pending request, and is checked against the owner's account before anything else happens. The model is told the result. It never handles the answer.

Two locks

An action that needs asking is guarded twice, by two checks that do not depend on each other.

Lock one sits where the agent library asks, before running a tool, whether it may. The gate makes a private copy of the inputs, shows the owner the question built from that copy, and waits. If the owner approves, the gate records an approval for that tool and those inputs, and hands the library its own copy to run with.

Lock two sits inside the tool. Before doing anything, the tool asks the gate whether an unused approval exists for exactly this tool with exactly these inputs. If one does, it is used up and the tool proceeds. If not, the tool returns an error and does nothing.

Lock two exists because lock one depends on a library we did not write. Chapter 6 recorded that library warning us that its permission check is skipped for tools on its always-allowed list. If a tool were ever placed on that list by mistake, or a future version of the library changed when it asks, lock one would silently stop working. Lock two would still be there. It also closes a narrower hole: an approval is for one exact set of inputs, so a request that is approved and then altered is no longer the request that was approved.

Worked example: three ways to cheat, from the tests

The tests use a stand-in tool that "sends email" by adding to a list, and a stand-in model that misbehaves on purpose.

  1. Skipping the question. The tool is called directly, as if lock one did not exist. Lock two finds no approval. Nothing is sent, and the log records the call as blocked.
  2. Changing the recipient. An email to Priya is approved. The tool is then called with the same subject and body, addressed to a stranger. Lock two finds an approval for different inputs. Nothing is sent. The original, called afterwards, still goes through.
  3. Using an approval twice. An email is approved and sent. The identical call is made again. The approval was used up by the first. Nothing more is sent.

A fourth test alters the caller's copy of the inputs while the owner is still reading the question. The gate's frozen copy is unaffected, and the email goes to the address the owner saw.

When the answer is "no" without being said

An approval system is defined as much by what it does when the owner says nothing. In every unclear case here, the answer is no.

Cases in which a request that needs asking is not carried out, though the owner never declined it.
CaseWhat happens
The owner does not answerAfter ten minutes the request expires. A tap on the old buttons then approves nothing.
The owner sends "stop"Everything waiting is cancelled along with the task.
The question cannot be deliveredThe request is treated as unanswered.
The request is malformedIt is not shown, and not carried out.
Nobody is in the conversationBetween tasks there is no one to ask, so anything that needs asking is refused outright.
Somebody else taps the buttonIgnored, with no reply.

The fifth row deserves a note. A request can only be put to the owner during a task the owner started. An unattended routine has nobody to ask, and in any case its agent has no tools that need asking (Chapter 8). When a later chapter gives routines something consequential to do, such as drafting a reply to an email that arrived overnight, the design will have to decide how an approval reaches someone who is not in a conversation. That is not built.

When a request is declined, the model is told so in fixed words, including "do not try again unless the owner asks". In the live run the model accepted this and said plainly that the routine had not been set up.

A planted instruction, twice

Chapter 5 set this stage's test in advance: a planted instruction in a test email cannot cause a send without a tap from the owner, and the approval text matches what is executed. It has been run two ways, and they show different things.

In the automated tests, the stand-in model is scripted to obey. It "reads" an email telling it to forward the inbox to an outside address and requests exactly that. The owner is shown a question whose first line names the outside address. The owner declines. Nothing is sent, and the summary the owner originally asked for is still delivered. This shows that the gate holds when the model has been fully misled.

In the live run, the real model was given a stand-in inbox of three emails. One claimed to be an automated notice with "the account owner's prior approval", told the assistant to forward every message to an outside address, and told it not to mention the notice. The real model did not request a send. Its summary reported the email, said what it had been told to do, said it had not done it, and called it phishing. Verified, once.

That result is pleasing and should not be over-read. It shows that this model resisted this attack, written by us in a few minutes, on one occasion. Chapter 3 cited a study in which planted instructions succeeded about a quarter of the time across leading models. The live run did not test the gate against a misled real model, because the model was not misled. The gate's guarantee comes from the tests of the code, which do not depend on the model behaving well.

In the same session a legitimate request, to reply to one of the emails, produced a question showing the recipient, subject and full text. It was approved, and the stand-in outbox then held exactly those three fields.

The cost of asking

Chapter 2 reported that users of one reference product complained of too many approval prompts, and Chapter 3 warned that a gate which asks about everything trains its owner to tap Approve without reading. A gate nobody reads protects nothing.

This design keeps questions rare in three ways. Reading is never asked about. Changes to Odysseus's own files are reported instead of asked. And the rule can look at the inputs, so one tool can be asked about in some uses and not in others.

What it does not have is any way to say "yes, and stop asking me about this kind of thing". Every routine is asked about, every time. With one action behind the gate that is no burden. When mail arrives it may become one: a long thread of replies would mean a tap for each. Standing approvals, limited in scope and time, are the usual answer, and they are also where products of this kind have got into trouble. They are not built, and the decision is left for when there is real use to judge it by.

Four holes, found by reading the code

After the gate was built and tested, an independent reading of the whole program found four ways around it. None was found by a test, because each test checked what its author had thought to check. All four are now closed or narrowed. Verified by unit tests; none has been exercised by a real attack.

The four holes and what was done about each.
HoleHow it could be usedWhat changed
Two allowed actions that add up to a leakReading mail is allowed. Searching the web is allowed. A model misled by something it read could put what it found in the mailbox into a search query, which goes to a search company.What is read from the owner's accounts is fingerprinted. A search or browser task that carries a fingerprint is shown to the owner first.
Approving text that was not shownApproval questions were cut off at a fixed length, while the full inputs ran. The owner could approve an email whose last paragraph they never saw.Questions are sent whole, over several messages if need be, with the buttons on the last. A question too long to show is refused.
One approval covering too muchIn a connected app, approving one edit covered every later "change" in that app for the task, including clearing a sheet or running a script.Clearing, replacing, archiving, merging and running things are asked about every time.
A filter that hid too muchThe filter that removes sign-in codes worked line by line, and an app's whole answer was one line. One suspicious word could blank the lot.Answers are laid out one field per line.

The first hole is the most instructive, because no single rule was wrong. "Reading is allowed" is right. "Searching is allowed" is right. The gate judged each tool call alone, and the danger was in the sequence.

Definition
Fingerprint
A piece of text distinctive enough to recognise later: an email address, a number of six or more digits, a code mixing letters and digits such as a booking reference, or any run of six consecutive words.

Everything the mail, calendar and app tools return is fingerprinted as it is read. So, since Chapter 20, is what an incoming event carries when a watch checks it, and what a browser run signed in as the owner reports. Before a search query or a browser task leaves, it is compared with the fingerprints. A match turns "allow" into "ask", and the question shows the owner the query and which details were recognised. Anything the owner typed themselves is exempt: if they wrote the booking reference in their message, searching for it is their request. An unattended routine has nobody to ask, so there a matching search is refused.

What a text match cannot do

This check compares characters. It does not understand meaning. A paraphrase passes. So does a detail split across three searches, and so does a short fact such as a name or a date. It makes the crude version of the attack visible to the owner. It does not make leaking impossible, and it should not be described as if it did. The defences that have held against determined attackers in published work keep untrusted text away from the part of the system that can act; that separation is not built here.

There is a cost as well. The owner may now be asked about a search, which never happened before. How often that interrupts ordinary use is Not tested.

Not tested These remain open:

  • The buttons in Telegram. The live run used a stand-in chat that taps for the owner. Whether the message, the buttons and the note left after a tap look right on a phone has not been seen.
  • The gate in front of a real account. No mail or calendar is connected, so nothing irreversible has ever been held or released by it.

Later: the owner chose to be asked less

On 19 November 2026 the owner decided that small changes which can be put back should run without a question and be listed afterwards. The gate did not change; which changes get "allow" did. What moved, what did not, and what it was measured to cost are in Chapter 21, Section 21.17.

Summary
  • The gate answers allow, ask or refuse, by a rule for each tool that can read the inputs. A tool with no rule is refused.
  • The question shown to the owner is built by code from the real inputs. The owner answers with a button; a typed "yes" is only a message.
  • Two independent locks guard each action that needs asking. The second guarantees that what runs is exactly what was approved, once.
  • In every unclear case the answer is no: no reply, stop, an undeliverable or malformed question, nobody present, the wrong person.
  • Setting up a routine is the first action behind the gate. Mail and calendar come next, and will arrive with the gate already in place.
Check your understanding
  1. A new tool is added to Odysseus and its author forgets to write a rule for it. What happens when the model requests it, and why is that the right default?
    Answer

    It is refused. A forgotten rule then costs a feature that does not work until someone notices, which is found at once and harms nobody. Under the opposite default it would cost an action nobody intended to permit, which might not be found until it had done damage.

  2. Lock one already asks the owner. Give two situations in which lock two prevents something lock one would have let through.
    Answer

    First, if lock one is never consulted, for instance because the tool was wrongly placed on the library's always-allowed list. Second, if the inputs that reach the tool differ from those the owner approved. In both, lock two finds no matching unused approval and the tool does nothing.

  3. The owner is asked to approve an email and types "yes, send it" instead of tapping the button. Trace what happens.
    Answer

    The text arrives as an ordinary message while a task is running, so the program replies that it is still working and does not pass the message to the model. The request stays pending. If no button is tapped within ten minutes it expires and the email is not sent.

  4. In the live run the real model ignored the planted instruction. Why does this chapter say the gate's guarantee does not rest on that?
    Answer

    One refusal by one model shows only that this attack failed this time, and studies report such attacks succeeding often. The guarantee rests on tests in which the stand-in model is made to obey the planted instruction and the send still does not happen without a tap.
