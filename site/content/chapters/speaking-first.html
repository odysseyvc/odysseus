What it means to speak first

Everything in Chapters 6 and 7 happens because the owner sent a message. Chapter 1 defined a routine as a task the agent starts by itself, and Chapter 2 found background work in all three reference products. An assistant that can only answer is a better search box. One that says "your flight leaves in three hours" without being asked is doing a different job.

Speaking first needs three things the slice did not have: somewhere to keep a list of things to do later, something that looks at the list as time passes, and a way to send a message nobody asked for. It also raises a question the earlier chapters could avoid. When the agent acts with nobody watching, who notices if it goes wrong?

Two kinds of job

Definitions
Reminder
A fixed message sent at a set time. The words are decided when it is created. Sending it requires no judgement.
Routine
A task for the agent to carry out at a set time: something that has to be looked up or worked out then, because the answer does not exist yet.

"Remind me at six to call my sister" is a reminder. "Every weekday at eight, send me the biggest AI headline" is a routine: the headline cannot be written the night before.

The distinction matters because the two are run completely differently.

A reminder that went through a model would cost money every time, could be delayed by a slow reply, and could in principle be talked out of sending. None of that buys anything, since the message is already written. So the rule from the plan is followed strictly: a reminder is sent by code, with no model call. The model's only part is at the start, turning "in two minutes" into a date and time and choosing the words.

The model works out the time from the stamp that Chapter 7 added to every message. Without it, "tomorrow at nine" would have no meaning to a program with no clock.

The list and the tick

Jobs are kept in a small database file with one row each: an identifier, the kind, the text, when it next runs, and how it repeats (once, hourly, daily, on weekdays, or weekly). A loop wakes every twenty seconds, asks for the rows whose time has come, and runs each one. That wake-up is called a tick.

After a job runs, it is moved on. A one-off is deleted. A repeating job is given its next time, which is always chosen to be in the future.

Worked example: the machine was off for four days

A daily reminder, "take the bins out", is set for 20:00. The program is then switched off for four days and started again.

A naive loop would find four missed runs and send four messages at once. This one finds a single row whose time has passed. It sends one message, and because the run is more than five minutes late it says so: the reminder was due at 20:00 on such a day and is late because the program was not running. It then sets the next time to the coming 20:00, skipping the days that were missed.

One late message with an explanation is more useful than four, and far more useful than none. The owner also learns that the program was down, which they may not have known.

Times are stored as plain local date and time, such as 2026-11-18T09:00, with no time zone attached. That is right for one person in one place, and it means "nine in the morning" stays nine in the morning. The program has one clock, used for the stamp on messages, the dates in memory and the schedule, and a setting can pin it to a named time zone so that it does not change if the program is moved to a server elsewhere.

An unattended run gets fewer tools

A routine is the first time in this book that the agent works with nobody watching. In a conversation the owner sees each reply and can type "stop". At eight in the morning, nobody is there.

So a routine does not run on the same agent as the conversation. It runs on a second one, built for the purpose, with three differences.

The conversation's agent and the routine's agent.
In conversationRunning a routine
ToolsSearch the web; save, change and search memory; set and cancel scheduled jobsSearch the web; search memory. Nothing that writes.
ModelThe mid-priced oneThe small one
What it starts withThe whole conversation so farIts instructions, the owner's profile and the time. Nothing else.

The first row is the one that matters for safety. A routine reads web pages, and Chapter 3 established that a model can be misled by what it reads. If a misled routine could save to memory, it could poison every later conversation (Chapter 7). If it could set schedules, it could create more routines, which could create more. With read-only tools, the worst a misled routine can do is send the owner one strange message.

This is enforced the same way as in Chapter 6, twice over: the writing tools are not built into the routine's tool server at all, and its gate refuses them by name if they are somehow requested. A test checks both.

Starting from nothing has a second benefit. Each run is independent, so a bad run cannot leave something behind that spoils the next. The agent is shut down when the run ends.

Because a routine starts with no conversation, its instructions must make sense alone. In the live run the main model, asked for a daily headline, wrote the routine a full paragraph of instructions without being told to.

Three outcomes, and why silence must be recorded

Chapter 5 set this stage's test in advance: every run ends as one of three recorded outcomes, and a failure is announced in the chat.

The three outcomes
Delivered
Something was sent to the owner.
Quiet
A routine ran, and decided there was nothing worth sending.
Failed
The job could not be carried out. The owner is told, with the reason.

The second outcome is the subtle one. Many useful routines are conditional: "tell me only if the price drops", "tell me only if a new version is out". On most days the right behaviour is to say nothing. The routine signals this by replying with a fixed marker, NO_REPLY, which the program recognises and does not forward.

But from the owner's side, a routine that ran and found nothing looks exactly like a routine that crashed, or one that never ran. This is the failure a builder described in the research, cited in Chapter 5: jobs that ran for a week, delivered nothing, and were assumed to have nothing to report.

The design removes the ambiguity from both ends. A quiet run is written to the record as quiet, with its time and cost, so that silence can be checked. And a failed run is never silent: the program sends a message naming the job and the reason. If the owner hears nothing, it means either nothing was due or a routine chose to stay quiet, and the record says which.

Worked example: one morning, from the live run

Two routines had been set the day before. One asked for the biggest AI headline each weekday at 08:00. The other, at 07:00 daily, asked to be told only if a newer stable version of a programming language had been released.

When the clock reached 08:01 both were due. The record afterwards read:

routine  due 07:00  quiet      $0.0013
routine  due 08:00  delivered  $0.0018

The owner received one message, a headline with a sentence of context and a link to its source. The first routine had searched, found no newer version, replied with the marker, and nothing was sent. Both then moved to the following day.

Later, in conversation, the owner asked what "that headline" had been about, and the model answered correctly. It could, because the program had told it what the routine sent (Section 8.6).

Two cautions. Nobody has checked the headline against its source. And "quiet" being the right answer was checked only by the routine's own search, on one day.

A routine is refused before it starts if the day's budget is already spent, and that refusal is a failure like any other: recorded and announced. Reminders are unaffected, since they cost nothing.

What the owner sees and controls

Setting a job is a change the model makes on the owner's behalf. As first built, every job was handled as memory was in Chapter 7: allowed without a question, and reported by code afterwards. Reminders still are. Since Chapter 9, setting up a routine asks the owner first. When a task has added or cancelled a job, the program appends a line to the reply that the model did not write, giving the job's identifier, kind, time and the start of its text.

The owner has two commands that go nowhere near the model. /schedule lists every job in full. /cancel followed by an identifier removes one.

The last piece connects the two agents. A routine runs apart from the conversation, so when the owner replies to what it sent, the conversation's model would have no idea what "that" refers to. The program therefore keeps what scheduled jobs have sent, and places it in front of the model with the owner's next message, once.

What was not built: the half-hourly check

The plan for this stage listed three things: reminders, routines, and "a quiet check every half hour", in which the agent wakes, looks around, and speaks only if something deserves it. The first two exist. The third does not, and the reason is worth stating.

A check needs something to check. At this stage Odysseus can see the public web and its own memory, and neither changes in ways that concern the owner between one half hour and the next. A check running forty-eight times a day would spend money to conclude, forty-eight times, that it has nothing to look at.

What was built is everything such a check is made of. A repeating routine is the timer. The NO_REPLY marker and the quiet outcome are the "speak only if it matters". When mail and calendar arrive in Chapter 10, the check becomes one routine with one sentence of instructions, and there will be something for it to find. (They have now arrived. A routine of that kind was run once on the real mailbox and stayed quiet; it is still not switched on by default.)

The periodic tidying of memory mentioned in Chapter 7 is also still unbuilt, for a different reason: it needs to write to memory, and unattended runs cannot write. Whether to make a narrow exception for it is an open question.

Summary
  • A reminder is a fixed message sent by code. A routine is a task run by the agent. Only the second uses a model or costs anything.
  • A loop checks a list of jobs every twenty seconds. After downtime, a missed job runs once, says it is late, and moves to its next future time.
  • A routine runs on a separate agent that can only read, uses the small model, and starts from nothing each time.
  • Every run is recorded as delivered, quiet or failed. Failures are announced, so silence never means failure.
  • The half-hourly check was not switched on, because there is nothing yet for it to check. Its parts exist.
Check your understanding
  1. Classify each as a reminder or a routine: (a) "At 5pm tell me to leave for the airport." (b) "Each morning tell me whether it will rain." (c) "On the first of the month, remind me to pay rent."
    Answer

    (a) and (c) are reminders: the words are known in advance. (b) is a routine: the forecast has to be looked up on the day.

  2. A routine is set to report "only if the train is delayed". For a week the owner hears nothing. Under this chapter's design, what are the possible explanations, and how can the owner tell them apart?
    Answer

    If the routine had failed, a message would have said so. So either it ran and stayed quiet each day, or it was never due. The record of runs shows a quiet entry with a time and a cost for each day it ran.

  3. Why is a routine not allowed to save to memory, when the same model in conversation is?
    Answer

    In conversation the owner sees a line reporting each save as it happens and can undo it. A routine runs with nobody watching, after reading web pages that may be hostile. A save made then would be reported in a message the owner might read hours later, after it had already influenced other conversations.

  4. The program was off from Monday to Friday. A weekday routine was due at 08:00 each day. How many times does it run when the program starts on Friday at noon, and when is it next due?
    Answer

    Once, marked as late if it delivers anything. Its next time is then the first weekday 08:00 in the future, which is Monday.
