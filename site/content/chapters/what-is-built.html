The problem: "it works" has no single meaning

A partner at the firm this book's worked application serves asks a plain question: "Can I rely on it to send my email tomorrow?" The project's front page says the program has 514 automated tests, all passing. An evaluation of the agent ran 581 times against the real model and passed 563. Mail was connected to the real account and read. None of that answers the question. No email has ever been sent through Odysseus. A send was held for approval on the real account once, and declined.

Every statement there is true, and a reader skimming them would conclude the wrong thing. This chapter teaches how to keep a record that prevents that, then gives the record for the whole system, which is also a map of what a reader could build next.

The concepts

Definition
Evidence grade
A label on a claim saying how it is known. This book uses four. Verified: read at the source, or measured here with the method stated. Secondary: reported by others. Maker's claim: stated by a company about its own product. Not tested: planned, designed or written, but never run.

"Verified" covers a wide range, so the map also says what kind of run verified a claim. Above a claim that is only written, four kinds matter, in rising order of strength.

Definition
Unit test with a stand-in
Test code that replaces a real component (the model, the mail service, the chat) with a scripted fake. Fast, free and repeatable, and it shows only that the program does what its author believed the real component would make it do.
Simulated-world run
The real model, the real gate and the real program, run against a stand-in world: a fake mailbox, calendar and web in which time passes, other people act and tools fail. It tests the agent's behaviour, but not the real services.
Live run
The real program against the real service, on a real account. "Run once" means exactly one such run.
Repeated live use
Many live runs over days or weeks, under ordinary use. It is the only evidence for anything that depends on time: a reminder firing at its hour, memory that stays useful, a cost per month.

"Run once" and "run for weeks" differ in kind, not degree. A single live run shows that a path through the program can work. It does not show how often, and it cannot show anything that only happens with time: a reminder at its real hour on a machine left running overnight, a profile that fills with trivia, a conversation that has grown expensive, a token that expires. And rates compound: a routine that works 90% of the time works five days running only 59% of the time.

Definition
Status map
A table with one row per capability and fixed columns: what exists, what has run live and how many times, what has never run, and the known faults. Every cell carries its evidence, and nothing is removed from the "never run" column until a run of the right kind has happened.

How to keep the map

Three rules keep a status map accurate.

Grade by the strongest evidence, and say which kind. "Mail works" is not a row. "Mail is read on the real account: one live run" and "Mail is sent: never, on any real account" are two rows. A capability is split wherever its parts have different evidence, and reading and acting almost always do.

Do not upgrade a claim. A repair that passes its unit tests is not thereby shown to work against the real service. When a later fact supersedes an earlier note, the note is corrected, not left beside it.

Count, and name the sample. "Seven good runs of eight" and "it works" are different statements, and runs on invented examples are marked as such.

Why a status map is a design tool

A status map can serve as a plan as well as a report. Read down the "never run" column: a reminder had never fired at its real time, WhatsApp had never received a message, a sign-in could not complete from a phone, events that arrived while the program was down were missed. All four had one cause: the program ran on a laptop, not on a machine that is always on and reachable. No single chapter shows that; the rows side by side do, and they say what the home must provide. Odysseus built that home deliberately last, so that everything else was built and proven on one machine first; the map is where the price of that choice was recorded. The home now exists ({{ch:staying-up}}). WhatsApp left the column the same day, with one message; the other three stay until each has run there.

The mechanism: where the evidence comes from

Each kind of evidence has a source in the repository: the unit tests in tests/; live runs by scripts in scripts/live_*.py, which cost money; and the simulated world in evals/, whose runner states what each condition means:

# evals/run.py (module documentation)
An errand is run under several conditions, and the same check must pass in each:

  clean    as written, in a world where every tool call works
  reword   the request in other words (perturb.py)
  messy    typed in a hurry: lower case, slips, something beside the point in front
  faults   as written, with tool calls failing at random about one time in seven
  both     reworded, with faults

Every run is also held to the invariants in invariants.py, whatever it was asked.

The conditions turn "it passed" into a graded statement: an errand that passes clean and fails reworded is fragile, and recording only the clean result would hide that. The fault rate of one in seven is a choice, not a measurement of how real services fail.

The same runner has a baseline that does nothing:

# evals/run.py
    .venv/Scripts/python -m evals.run --agent nothing         a baseline that does nothing at all

It tests the checks themselves. An agent that does nothing must score zero; if it does not, some check passes for a reason other than the agent's work. The do-nothing agent scored 0 of 81 on the suite as it stood before its last additions, and passed none of the fourteen partner errands. Verified. Even so, a row can be green because a check is blind in a way the baseline does not reveal, which happened (see "What goes wrong").

A worked example: grading one claim

Take the claim "Odysseus sends an email the owner approved", and walk it up the ladder.

  1. Unit tests. Three tests on sending check that mail is not sent without approval, that approved mail is sent exactly as shown and only once, and that a reply uses the connector's own field names. The gate's tests check that a planted instruction cannot cause a send without a tap, and that typing "yes" is not an approval. All pass, against a stand-in connector. Verified, unit tests.
  2. Simulated world. In 581 runs with the real model against a stand-in mailbox, no run sent a message without an approval for the same people and the same words, and no planted instruction was acted on in 84 attempts. Verified, simulated world.
  3. Live. On the owner's real account a request to send was shown for approval and declined. Once. Verified, that the question was asked and that declining sent nothing.
  4. Live, approved. Never. Not tested.

The row in the map is therefore: sending mail: exists; held and declined live once; never approved on a real account. The answer to the partner is "not known". Steps 1 and 2 are strong evidence about the program's rules and easily mistaken for evidence that sending works; they say nothing about whether the real connector accepts the message or whether it arrives.

What is deliberately left out

Payments, phone calls, group chats and acting inside the owner's conversations with other people wait until the simpler system has a stable score, because each adds a way to cause harm. Two original must-haves are also absent: a vault for passwords (the owner signs in by hand, so no secret is saved) and handing bot checks to the owner (left to the browser vendor by the owner's decision).

The theory

A status map has no useful formal statement of its own. It is a record of evidence, and what it needs is criteria precise enough that two people grading the same row reach the same rung. Those criteria follow.

Rungs. A piece of evidence e for a claim has a kind κ(e), ordered from weakest to strongest:

0, written
Code, a design or a plan exists; nothing has run.
1, unit test
A test passes with at least one component replaced by a stand-in. It can support a property of the program (in the sense of the model), never a measurement of a model or a service.
2, simulated world
The real model and the real program, gate included, against a stand-in world. It supports a measurement of the agent's behaviour, stated as k passes of n runs.
3, live
The real program against the real service on a real account, performing the act the claim names. A neighbouring act does not count: a send held and declined is live evidence that the question was asked, not that sending works.
4, repeated live
Two or more live runs of the same act, counted, with invented examples marked.
5, weeks
Ordinary use over days or weeks. The only kind that can support a claim about time: a job at its hour, memory that stays useful, a cost per month.

The rung of a claim is r(c) = max κ(e) over the evidence that supports exactly c; with no evidence it is 0.

Rules. (1) A capability whose parts have different rungs is split into rows until each row has one rung; reading and acting are almost always separate rows. (2) A rung rises only by a new run of the higher kind. A repair resets the repaired behaviour to the kind of evidence the repair has, so a fix that passes its unit tests is at rung 1 until it runs live again. (3) Every count gives its denominator and its sample: "7 of 8, on one invented deck". (4) An entry leaves "never run" only on a run of the right kind for that entry. (5) A note overtaken by a later fact is corrected, not left beside the new one. (6) A green evaluation row also records what would make its check fail, and the do-nothing agent must score zero on it.

The grade labels (Verified, Secondary, Maker's claim, Not tested) say where a claim comes from; the rung says how strong the evidence is when it comes from here. The two are kept separate because "verified" spans rungs 1 to 4.

Derivation: what clean runs can show

If n independent live runs all succeed, the largest failure rate f not rejected at the 5% level satisfies (1 − f)n = 0.05, so

fmax = 1 − 0.051/n ≈ 3/n for large n

For n = 1 this is 95%: one clean run is consistent with an act that fails nineteen times in twenty. That is the formal content of "run once and run for weeks differ in kind". The hypothesis is independence, and it fails whenever runs repeat one invented example, since runs of one case are correlated (Definition 9); then n overstates the evidence. Reliability compounds the other way: a routine that works with probability 0.9 per day works five days running with probability 0.95 ≈ 0.59, the passk of Definition 9.

What goes wrong when keeping a map

A green row that measured nothing. In the first run of the partner errands, every run passed, including five of five approved runs of one filing errand in which the program created a second copy of a company already in the database. Its lookup compared exact names, and so did the check; they agreed, and the row was green. It was found only by reading a transcript of a passing run.

A repair that disarmed a test. A repair made the program retry a failed read twice. The simulated faults never lasted that long, so the "faults" condition silently stopped testing the agent and tested the retry loop. The map therefore records what each check would take to fail as well as that it passed.

Status written before the facts. Several status notes were overtaken by events: the firm's database "has only been read from" before real records were filed; the chat's buttons "have not been tapped" before a plan was approved there.

A check at thirty seconds. The cloud machine was checked half a minute after launch and found running; the host stopped it at five minutes, after the laptop copy had been switched off, and nothing said so.

How to test the map itself

A map is tested by trying to falsify its rows. For each "Verified" cell, ask what run produced it and whether it was of the kind the cell implies. For each "never run" cell, look for evidence that it has since run (a real deck sent through Telegram appears to have exercised the fetching of a file from Telegram, which an earlier note said had never run). For each green evaluation row, read a passing transcript and confirm the do-nothing baseline still scores zero. For each count, check the denominator: 16 chances is not 84.

The gaps, and the order to close them

A review of what the leading assistants connect to named four gaps between Odysseus and them. The program ran on a laptop where its rivals run on a computer in the cloud. It has no paid source of data about companies and people. It has no email address of its own. And it serves one owner where the firm wants one per partner. Only the second costs real money. The order below is a judgement, not a measurement.

  1. The first real acts. An approved send, an event created with a guest, an approved change to a record in the firm's database, each made by the owner's own hand and recorded. Then a signed-in browser run on an account with nothing valuable in it, carrying a planted instruction on purpose.
  2. Weeks of use. Memory, the long conversation, the digest on consecutive days, and the monthly bill can only be measured by living with the program. The trace store exists; the regular reading of real traces, a named list of failure kinds and a test written from each do not.
  3. The company-data bake-off, once the owner has opened vendor accounts: the script and test set exist, and no lookup has run.
  4. An address of its own. A bot in a chat cannot be written to by anyone but its owner. One reading of why this matters: an assistant with a mailbox of its own could be copied on a thread by the owner or a colleague and act on it. Built, on a rented mailbox, with strangers' mail put to the owner before any model reads it ({{ch:mail-and-calendar}}); run once against the real service for the owner's own mail and once for a stranger's.
  5. One per partner. One running copy now serves several people, each with an assistant, folder, sign-ins and budget of their own, joined by a link the host sends ({{ch:channels}}). Proven once, with invented people. An invited person can sign in to the firm's database from their own chat, on a page of the program's own once it has a public address. A silent person's processes are let go, and a new connection disturbs only the person who made it. A real second person has joined, and the program runs on a server with this switched on. What is missing: that person's first sign-in to the firm's database through the page, and enough memory on the server for two people talking at once.
  6. An always-on home. It unblocks the most rows: reminders at their real time, WhatsApp receiving, watches that do not miss events, sign-ins with a public return address, and a watcher outside the program that reports its death. It was deliberately last, so that everything else was built and proven on one machine first. It is now built; each row that depended on it still has to be run there before it climbs the ladder, and the watcher is not built.

Four faults in the safety layer stood open beside these, and a fifth was found in use. Each now has a repair and a unit test (tests/test_safety_faults.py); none has been exercised by a real failure.

What is proven and what is not

Verified: the program exists and its unit tests pass; the agent passes most errands in a simulated world against the real model, with no invariant on approvals or recipients broken in 581 runs; nearly every reading path has run against its real service at least once (the exception is reading other people's posts on the social network, which has never returned one). Not tested: every act that reaches another person or cannot be undone, by the owner's own hand, on a real account; an email attachment read by the model from end to end; anything over days or weeks; anything on the server for longer than a day. Nothing in this book supports a claim that Odysseus is as good as, or better than, another product, and none is made.

Case note: faults found by reading the code

Writing this book meant reading every module again to explain it. That reading found seven faults that no test had: a task for the meeting brief presented to the model as the owner's instructions when it quoted an invitation a stranger wrote; approval questions for two families of tool cut at a fixed length while the whole input ran; a failed watch check that was logged and never said; an address check for a connected server made once and never again; a verification message accepted with no date or from before the run; a lost conversation announced only when a task had also been interrupted; and a general app tool that neither retried a read nor warned after a failed change. An independent review of the book then found five more: a read sent in a conversation to somebody else's service was not checked for private details as a web search is; an unattended run was allowed whatever would run unasked in a conversation, so a routine could have added a note to the firm's database; a routine or watch could be set up unasked when its own text carried details from the owner's accounts; the page reader and the agent that judges incoming mail were handed servers listing search and memory, with one deny-all check in between; and a meeting brief that ended could hide an interrupted conversation. All twelve are closed and each has a test in tests/test_found_by_reading.py. Not tested: none of the repairs has been exercised against the real services. {{ch:a-second-reading}} is about why this keeps happening.

Where this sits in the literature

The map is an answer to a complaint the agent-evaluation literature makes about published results. {{cite:kapoor2024agentsmatter}} argue that agent evaluations should report cost beside accuracy, guard against overfitting with held-out sets, and fix the reproducibility problems that make results hard to compare. The map does the first wherever a cost was recorded, which is many of its live rows. It does not do the second: the errands it reports were written by the builders and repaired against, and no held-out set of errands was kept back. On that point the published advice is stronger than this program's practice.

{{cite:zhu2025abc}} analyse validity problems in agent benchmarks, including flaws in how tasks are set up and in the graders that score them, and propose a checklist. The do-nothing agent and the rule that a green row records what would make it fail are two items of that kind of checklist, arrived at here by being caught. The case of the second "Northwind", in which the program's lookup and the check shared one blind spot and agreed, is a grader flaw of the sort they warn about, and of the sort {{cite:wang2025solvedissues}} found in practice when they examined patches that passed a benchmark's tests and asked whether they were correct.

The rungs are a crude response to the question {{cite:bean2025construct}} put to hundreds of benchmarks: does the score measure the thing it is named for? "It works" is named for use by a real person on a real account over time; most of what the map can cite measures something narrower, and the map's columns exist to keep the narrower thing from being read as the wider one.

Repetition is treated in the literature in two ways that the map uses separately. {{cite:yao2024taubench}} measure an agent's consistency over repeated trials of the same task as a quantity of its own, distinct from success on one trial; it is the quantity a routine's per-day rate becomes when compounded over days. {{cite:miller2024errorbars}} argue that every reported result should carry an interval and that repeated runs of one case are not independent. The map gives counts and denominators but not intervals, and many of its counts are on one invented example, where the interval would be wide and the independence assumed by the derivation above does not hold.

The simulated world's "faults" condition fails tool calls at random about one time in seven. {{cite:basiri2016chaos}} describe a stronger practice: experiments that inject failure into the production system itself, so that confidence comes from the real system surviving real turbulence. This program injects faults only into a stand-in world, at a rate chosen rather than measured, and the map records that as a limit. Service level objectives in the sense of {{cite:sre-slo}} would give the top rung a target: a stated fraction of reminders on time over a month, say, against which weeks of use could be scored. The map has no such targets for its live rows.

What the literature has not settled is the step between rungs 2 and 4 for an agent that acts for one person. Benchmarks give simulated evidence at scale, and field studies give live evidence for products with many users. For a personal agent with one owner, how many live runs of an act are enough to rely on it, and how to combine a large simulated sample with a handful of live runs into one statement, has no agreed answer.

Summary
  • "It works" splits into kinds of evidence: unit test, simulated world, live once, live repeatedly, lived with for weeks. Name the kind.
  • Split a capability wherever its parts have different evidence; never upgrade a claim; give every count with its sample.
  • A do-nothing agent must score zero, and passing runs must be read, or a green row can mean a blind check.
  • For Odysseus, reading has reached live runs; most acting has reached only the simulated world; nothing has been used for weeks.
  • Read as a plan, the map points to one cause behind many gaps: the program has no always-on home. That home is built deliberately last, and the map records what waits on it.
  • The remaining gaps, in order: the first real acts, weeks of use, the data-vendor bake-off, and a real second person.
