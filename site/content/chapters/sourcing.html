After this chapter you should be able to
  • Say which parts of sourcing for an early-stage investor a program can do, and which it cannot.
  • Build a daily digest as an unattended routine that reads several services, checks the firm's database, and does not repeat itself.
  • Connect a paid social network so that it can only read, meter its reads, estimate their cost, and fall back when it refuses.
  • Explain what public web search finds and what it misses, and why that makes a data vendor the one significant purchase.
  • Design a comparison of data vendors that measures coverage on companies the firm already knows, within a free tier's daily limit.

The problem

An early-stage investor can only invest in companies they have seen, and the common belief in the trade (stated here as background, not as a finding) is that seeing a company early matters: a partner who noticed an announcement on its first day, and wrote first, is better placed than one who hears of it a month later from another firm. Finding those companies is called sourcing, and much of it is reading: posts, launch pages, news, and records of who has just left which job.

The scenario this chapter builds toward: each weekday morning the partner receives one short message listing the few people and companies worth their attention, each with where it came from, why it matched what the firm invests in, and whether the firm already knows them. Nobody asked for it that morning. Tomorrow's message does not repeat today's. If the social network the digest reads refuses to answer, the message still arrives and says what was lost.

Definitions

Sourcing is the work of finding companies to invest in before, or as, they look for money. A signal is an observable event that suggests a company may be worth a look: a launch, a founder announcing a new company, a senior engineer leaving a large employer, a first round. A digest is a periodic message that collects the signals found since the last one.

A program can do the parts that are reading and matching: searching public sources, reading a network the partner follows, checking each find against the firm's database, and writing it up. It cannot do the parts that are judgement and relationship: deciding whether a founder is exceptional, or being the person a founder wants to call. That division is an explanation, not a measurement, but it sets the design: the digest proposes and the partner decides, and it files nobody the partner has not picked.

Three ideas the design rests on

A routine runs with nobody watching. {{ch:acting-unasked}} introduces routines: instructions the owner approved once, run at a set time by a cheaper model, which start fresh each time. The consequence that matters here is that a routine has no owner to ask. In a conversation, anything doubtful is put to the owner by the gate of {{ch:the-gate}}. In a routine, every doubt has to be settled by code, in advance, as a refusal.

Definition

A metered read is a call to a service that is charged per item returned. A read budget is a fixed number of calls one unattended run may make of a service, set in code.

Some reads cost money. X, the social network, charges for each post and profile a program reads through its interface for programs. A model that keeps looking keeps spending. So reads are counted, and each one's likely cost is written down.

What a search sends is a message. A query to a service is information given to that company. {{ch:untrusted-content}} explains taint: everything read from the owner's accounts is remembered, and a later request that carries it is asked about. In a routine, "asked about" becomes "refused".

The design of the digest

Four choices define it, each against an obvious alternative.

Reading only, twice over. The partner asked whether the assistant could control their X account. Finding opportunities needs the timeline, lists, bookmarks, who the partner follows, and search. It needs no permission to post, reply, follow or message, and an assistant that reads what strangers write should not hold any. The firm's database is read the same way: the filing tools of {{ch:a-firms-database}} are not offered to a routine at all. X's own means enforce reading twice: its server has a read-only address that offers only reading tools, and the sign-in asks only for reading permissions. Driving X's website in the partner's signed-in browser was rejected: X's rules forbid it and it puts an account built over years at risk.

A fixed number of reads. A budget in money would let one run spend the day's limit on a single unlucky search. A count is simpler to reason about: eight reads of X, twelve of the firm's database, six of a data vendor, per run.

Web search as the fallback, not a browser. The partner asked for a second route when X fails, or whichever route is cheaper. The comparison:

The browser is neither cheaper nor able to run alone, so web search is the fallback. When X refuses, the routine says so in one line, does not retry, searches the web for the same thing, and marks every find that did not come from X.

Showing the routine what it sent. A routine that remembers nothing sends the same finds every morning. A memory of everything it read would carry strangers' text forward indefinitely. The middle course is to keep only the last three messages actually sent, and show them to the next run with an instruction not to repeat an item unless something changed.

The mechanism

A service described by an entry

Services with their own server ({{ch:services-with-their-own-server}}) are entries in a table, APPS in odysseus/mcpapp.py. X's entry pins the connection to reading:

APPS["x"] = {
    "title": "X",
    # ?read_only=true makes X's server offer only tools that read. The scopes asked for below
    # are the reading ones too, so the token itself cannot post, follow, like or message.
    "url": "https://api.x.com/mcp?read_only=true",
    "scope": "tweet.read users.read follows.read list.read bookmark.read like.read offline.access",
    "read_only_connection": True,
    "client_id_env": "X_CLIENT_ID",
    "price": {"default": 0.005, "free": ("get_usage_credits",),
              "own": (0.001, ("users_me", "bookmark", "liked_posts", "mentions", ...)),
              "people": (0.010, ("get_users_by", "search_users", "followers", ...))},
    "unattended_calls": 8,
    "hide": ("chat_media_download",),

read_only_connection exists because X labels none of its tools. The general rule for a server's tools (a tool runs unasked only if the vendor labels it read-only and its name begins with a reading word) would have put every call to the owner. A connection that cannot write needs no label to say so. The entry's prompt tells the model to ask for small pages, to read a profile only when a post has earned it, and, if X refuses for lack of credit, to fall back to web search and mark each find that came from the web.

Estimating what a read cost

X's server does not say what a call cost. The program estimates it from what came back:

def estimate(spec: dict[str, Any], name: str, text: str) -> float:
    price = spec.get("price")
    if not price or name in price.get("free", ()):
        return 0.0
    try:
        data = json.loads(text).get("data")
    except (ValueError, AttributeError):
        return 0.0
    items = len(data) if isinstance(data, list) else (1 if data else 0)
    each = price["default"]
    for key in ("own", "people"):
        rate, marks = price.get(key, (None, ()))
        if rate is not None and any(m in name for m in marks):
            each = rate
            break
    return round(items * each, 4)

The result is written to the journal with estimated: True, and the ledger of {{ch:cost}} counts it toward the day's limit. A refusal ("Too many requests") parses to nothing and costs nothing. The bill is X's and has never been compared with this estimate.

Three refusals for a run with nobody watching

unattended in the same file wraps a service's run tool for a routine:

if app.decide(args) != ALLOW:
    return no(f"Not done. Either that {title} tool changes something, and nobody is here to "
              "approve it, or it has not been looked up yet with the find tool.")
taint = getattr(app, "taint", None)
seen = getattr(app, "unattended_seen", None)
...
if not own_store and taint is not None and taint.leaked(_foreign(args.get("arguments") or {}, seen)):
    return no(f"Not sent to {title}: the request contains details from the owner's mail, "
              "calendar or database, and nobody is here to approve sending them.")
left = getattr(app, "unattended_left", None)
if left is not None:
    if left <= 0:
        return no(f"No more reads of {title} in this run: the limit for an unattended run has "
                  "been reached. Work with what you have.")
    app.unattended_left = left - 1
out = await run(args)
if not out.get("is_error"):
    seen.append(out["content"][0]["text"])

The second check has an exception that matters. Everything a service returns is remembered as private, X included, because a timeline says something about its owner. A digest's second step is usually to look up the author of a post the first step returned, by the identifier X gave. Without the exception that lookup would be refused, since the identifier was "read from the owner's accounts". _foreign removes from the check any value the same service returned earlier in the same run: giving a service back its own identifier tells it nothing. A detail from the owner's mail in a search of X is still refused. The firm's database and the owner's meeting notes are exempt from the check altogether (own_store), because looking up there is the point.

Not repeating itself

In odysseus/schedule.py, after a message is sent, its text is kept:

data[job_id] = (data.get(job_id, []) + [text[:3000]])[-3:]
self._history_file.write_text(json.dumps(data, ensure_ascii=False), encoding="utf-8")

Only a delivered message is kept; a run that answered NO_REPLY or failed adds nothing. In odysseus/routines.py the next run is shown them:

before = ("\n\nWHAT THIS ROUTINE SENT THE LAST TIMES IT RAN, oldest first. Do not send an item "
          "again unless something about it has changed, and say what changed. If there is nothing "
          "new, say so in one line.\n" + "\n---\n".join(p[:1500] for p in previous[-3:])) if previous else ""

This is the first thing a routine carries from one run to the next, and it is a risk worth naming: the carried text was written from what strangers posted, so a planted sentence could reach a second run through it. The run it reaches still has reading tools only.

What public search can and cannot find

Web search finds companies that have announced themselves: a launch page, a news item, a post that a search engine has indexed. It finds them hours after X would, and it does not see the partner's own timeline or lists. That makes it a reasonable fallback for the digest, and a poor source for the signal that matters most to an early-stage investor: the person who left a job last week and has not yet said what they are doing. That person has no launch page. The signal exists only in records of who works where, which is what data vendors collect and sell. The vendor prompt in mcpapp.py says as much from the other side: if a vendor has no record of a company that has not raised, "that is common and means little".

A review of what leading assistants and venture firms connect to found few gaps in this system: it runs on a laptop where its rivals run in the cloud, it has no paid source of data about companies and people, it has no email address of its own, and it serves one owner where the firm wants one per partner. Only one of those costs real money, which is why a data vendor is the one significant purchase. The decision belongs to {{ch:build-or-buy}}: a database of companies and people is not something to build.

The evidence for which vendor to pay is thin exactly where this firm needs it. Most comparisons are written by one of the vendors compared, and the one independent benchmark found is European and says nothing of India. So the choice is made by measurement.

Choosing a data vendor by measurement

Seven vendors run servers of the kind {{ch:services-with-their-own-server}} connects, and each is an entry in APPS so the owner can connect it by name: Harmonic, Tracxn, Specter, Crunchbase, Crustdata, Evertrace and Dealroom. Their descriptions in the code differ in emphasis: Tracxn's is "built in India and deepest there"; Specter, Crustdata and Evertrace are described with signals such as job changes.

The method, in scripts/bakeoff.py, is to look up companies the firm already knows in each vendor and count what comes back. The firm's own records are the answer key. The test set is written from the firm's database, read only, and kept out of the repository because it is the firm's pipeline. Each answer is judged by code:

def judge(answer: str, company: dict[str, str]) -> dict[str, object]:
    low, flat = answer.lower(), norm(answer)
    site, name = company.get("domain", "").lower(), norm(company.get("name", ""))
    found = bool((site and site in low) or
                 (name and len(name) >= 4 and re.search(rf"\b{re.escape(name)}\b", flat)))
    people = [p for p in (x.strip() for x in company.get("people", "").split(";")) if p]
    return {"found": found,
            "people": bool(found and any(norm(p) in flat for p in people)) if people else "",
            "funding": bool(found and _MONEY.search(answer)),
            "chars": len(answer) if found else 0}
What each column of the comparison means.
ColumnCounted whenWhat it does not show
foundThe answer names the company's own website, or its exact name (four characters or more, as a whole word)That the record is correct or current

Website before name. A lookup is made by website when the firm has one on record, by name otherwise. A name finds the wrong company: many startups share a word. choose picks each vendor's lookup tool from the names of its tools and inputs, scoring an input that takes a website above one that takes text. A vendor whose lookup takes only a website is not asked about a company the firm has no website for; that row is skipped rather than guessed.

Designed around a daily limit. Several vendors' free tiers allow about a hundred reads a day. A run stops at a limit (90 by default, --limit to change it), every result is appended to a file as it arrives, and a later run skips rows already done. So a comparison of seven vendors on a few dozen companies is a run a day for a few days, with no paid plan needed to decide which plan to pay for.

The design measures coverage, not truth. A vendor that returns a confident, wrong round scores the same as one that is right; the firm's own records seldom hold enough to tell. Checking a sample by hand would close part of that gap.

Data about people and where it comes from

The signal about a person leaving a job appears first on professional networks. What access those networks give programs has not been examined here, and neither has where any vendor gets its records of job changes. What follows is therefore an argument, not a finding, and it names no service and cites no shutdown. A vendor whose records come from collecting pages of a site whose rules forbid it depends on that site's tolerance, and the firm that buys from it inherits the dependency. What has been established is narrower and applies by analogy. For X, driving the website as the user is forbidden by its rules and risks the account; the sanctioned interface was chosen even though it charges per read. The same test applies to a vendor: ask how it gets its data, and prefer one whose answer does not rest on another company's forbearance.

A worked example: one morning, with X out of credit

Worked example: the live routine run

Input. scripts/live_routine.py runs one routine's instructions once, exactly as the scheduler would, with the real model and the real connected services, and sends nothing. The instructions were invented: find new companies in one sector. The X account had no credit.

Step 1. The routine agent starts with a fresh session, a fresh allowance of reads (eight of X, twelve of the database), the memory, and the instructions. It turns to X first.

Step 2. X refuses every read with "credits depleted".

Step 3. Following its instructions, the routine says in one line that X was unavailable and why, and makes one web search.

Step 4. It finds three launches, and notes that all three fall outside the day it was asked about.

Step 5. It looks two of them up in the firm's database, reading only, and finds neither. It writes "not checked" beside the third.

Output. One message: X was unavailable and why, then the three launches, with what the database showed for each. 38 seconds; about 1.3 cents, of which 0.6 the model and 0.7 the search.

The same instructions run once before the fallback existed produced a message reporting X's refusal and listing nothing.

What the run also showed is as instructive as the result. Two of its four reads of the database failed on badly formed inputs, and a failed read still uses one of the twelve. It ended by offering to run again later, which a routine cannot do. And the fallback is a sentence in its instructions: the model followed it once.

What goes wrong

Case note

The first sign-in link produced for X asked for every permission X offers: reading, and also posting, sending direct messages and changing billing. The entry listed seven reading permissions. The sign-in library had replaced that list with the server's full list of what it supports, because the protocol tells a client to ask for what the server advertises. Both were behaving as designed; together they turned "read only" into "everything". It was caught because the link was read before it was opened; no approval was given and no token saved. The program now rewrites the link to ask for exactly the permissions the entry names, a test checks that a wider list is replaced and not added to, and the connect script prints what a sign-in asks for above the link. X's approval page then listed only reading, and the token returned carries the seven reading permissions and no others. A configuration is a statement of intent; whether it reached the wire is a separate fact.

A wider rule counted one thing twice. The ledger had counted the cost of one tool, web search. Making it count any tool call that reports a cost made every browser run cost double, because a browser run's cost is already part of its task. An older browser test caught it, with 0.07 where 0.04 was expected. The rule now names the exception.

An approval that did nothing. When the owner had the digest scheduled through the chat, the model wrote instructions of 972 characters; the schedule accepts 600. The owner was shown all 972, approved them, and only then did the schedule refuse. An approval followed by a refusal teaches the owner that approving does not mean it happened. The length is now checked while the question is built, and the tool's description gives the limit.

An approval that understated. The same question said a run "can only read (your mail and calendar, the web and my notes)". It could also read X, the meeting notes and the firm's database. The page now lists every service a run can read, from the same list the run is built from. A description of a permission must be generated from the thing it describes.

How to test it

A test of an unattended reader must check refusals as carefully as successes, because the refusals are the design. tests/test_mcpapp.py checks that an unlooked-up tool and a changing tool are refused without a call reaching the service; that the third read is refused when the allowance is two, and the next run starts afresh; that a search carrying an address from the owner's mail is refused while X's own identifier may go back to it; that the owner's own notes are exempt; that the estimate is half a cent a post, a cent a profile, a tenth of a cent for the owner's own data and nothing for a refusal; and that a paid read is counted once and a browser run not twice. tests/test_schedule.py checks that a daily routine is shown its last three messages, across a restart, and that quiet or failed runs add nothing.

What none of this shows: any read of X that returned posts, so neither the estimate nor the limit of eight has met real data; three consecutive days of the digest, which is the only real test of not repeating; and whether the partner finds the finds worth reading.

What is proven and what is not

Verified, live: X connected with reading permissions only; 59 tools offered, one hidden, every one a read; the owner's own profile read through the gate in half a second. The digest routine run twice with invented instructions while X had no credit: the first reported the refusal and listed nothing; the second fell back to web search as described (38 seconds, about 1.3 cents). The scheduling fixes, by test; the routine itself was created live through the chat and has not yet run on its schedule.

Verified: seven vendors' addresses answer as servers of this kind, three at addresses their documentation gives and four at addresses on their own domains that were tried; the India-built one is not in the public registry. A test set of 29 companies was written from the firm's database, 28 with a website and 12 with people on record.

Not tested: the vendor comparison has not made a single lookup. No vendor is connected, since each needs an account that only the owner can open, and the script's choice of lookup tool has been tried only on invented tool names. Also not tested: any paid read of X; the cost estimate against X's bill; three days of the digest; and any claim here about data on people from professional networks.

Summary
  • Sourcing is mostly reading and matching, which a program can do; judging founders and being trusted by them it cannot.
  • A digest is a routine: nobody is watching, so every doubt is settled by code as a refusal: not a plain read, a detail from the owner's accounts, or reads used up.
  • X is connected to read only, by its read-only address and by reading permissions; the case note shows that the second must be checked on the wire.
  • Metered reads are counted and their cost estimated from the items returned; the estimate is marked as one.
  • When X refuses, the routine says so and falls back to web search, which is cheaper and later and cannot see the partner's own timeline.
  • Keeping the last three messages sent stops repetition and is the one path from one run to the next.
  • Public search finds companies that announced themselves, not people who just left a job; that gap is why a data vendor is the one significant purchase, chosen by looking up companies the firm knows and counting what comes back. No lookup has yet been made.
