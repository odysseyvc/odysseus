The problem

An early-stage investor can only invest in companies they have seen, and the common belief in the trade (stated here as background, not as a finding) is that seeing a company early matters: a partner who noticed an announcement on its first day, and wrote first, is better placed than one who hears of it a month later from another firm. Finding those companies is called sourcing, and much of it is reading: posts, launch pages, news, and records of who has just left which job.

The scenario this chapter builds toward: each weekday morning the partner receives one short message listing the few people and companies worth their attention, each with where it came from, why it matched what the firm invests in, and whether the firm already knows them. Nobody asked for it that morning. Tomorrow's message does not repeat today's. If the social network the digest reads refuses to answer, the message still arrives and says what was lost.

Definitions

Sourcing is the work of finding companies to invest in before, or as, they look for money. A signal is an observable event that suggests a company may be worth a look: a launch, a founder announcing a new company, a senior engineer leaving a large employer, a first round. A digest is a periodic message that collects the signals found since the last one.

A program can do the parts that are reading and matching: searching public sources, reading a network the partner follows, checking each find against the firm's database, and writing it up. It cannot do the parts that are judgement and relationship: deciding whether a founder is exceptional, or being the person a founder wants to call. That division is an explanation, not a measurement, but it sets the design: the digest proposes and the partner decides, and it files nobody the partner has not picked.

Three ideas the design rests on

A routine runs with nobody watching. {{ch:acting-unasked}} introduces routines: instructions the owner approved once, run at a set time by a cheaper model, which start fresh each time. The consequence that matters here is that a routine has no owner to ask. In a conversation, anything doubtful is put to the owner by the gate of {{ch:the-gate}}. In a routine, every doubt has to be settled by code, in advance, as a refusal.

Definition

A metered read is a call to a service that is charged per item returned. A read budget is a fixed number of calls one unattended run may make of a service, set in code.

Some reads cost money. X, the social network, charges for each post and profile a program reads through its interface for programs. A model that keeps looking keeps spending. So reads are counted, and each one's likely cost is written down.

What a search sends is a message. A query to a service is information given to that company. {{ch:untrusted-content}} explains taint: everything read from the owner's accounts is remembered, and a later request that carries it is asked about. In a routine, "asked about" becomes "refused".

The design of the digest

Four choices define it, each against an obvious alternative.

Reading only, twice over. The partner asked whether the assistant could control their X account. Finding opportunities needs the timeline, lists, bookmarks, who the partner follows, and search. It needs no permission to post, reply, follow or message, and an assistant that reads what strangers write should not hold any. The firm's database is read the same way: the filing tools of {{ch:a-firms-database}} are not offered to a routine at all, and the general tool for the database runs only tools that read. X's own means enforce reading twice: its server has a read-only address that offers only reading tools, and the sign-in asks only for reading permissions. Driving X's website in the partner's signed-in browser was rejected: X's rules forbid it and it puts an account built over years at risk.

A fixed number of reads. A budget in money would let one run spend the day's limit on a single unlucky search. A count is simpler to reason about: eight reads of X, twelve of the firm's database, six of a data vendor, per run.

Web search as the fallback, not a browser. The partner asked for a second route when X fails, or whichever route is cheaper. The comparison:

When X refuses, the routine is instructed to say so in one line, not to retry, to search the web for the same thing, and to mark every find that did not come from X; it did so in the one run made with that instruction.

Showing the routine what it sent. A routine that remembers nothing sends the same finds every morning. A memory of everything it read would carry strangers' text forward indefinitely. The middle course is to keep only the last three messages actually sent, and show them to the next run with an instruction not to repeat an item unless something changed.

The mechanism

A service described by an entry

Services with their own server ({{ch:services-with-their-own-server}}) are entries in a table, APPS in odysseus/mcpapp.py. X's entry pins the connection to reading:

APPS["x"] = {
    "title": "X",
    # ?read_only=true makes X's server offer only tools that read. The scopes asked for below
    # are the reading ones too, so the token itself cannot post, follow, like or message.
    "url": "https://api.x.com/mcp?read_only=true",
    "scope": "tweet.read users.read follows.read list.read bookmark.read like.read offline.access",
    "read_only_connection": True,
    "client_id_env": "X_CLIENT_ID",
    "price": {"default": 0.005, "free": ("get_usage_credits",),
              "own": (0.001, ("users_me", "bookmark", "liked_posts", "mentions", ...)),
              "people": (0.010, ("get_users_by", "search_users", "followers", ...))},
    "unattended_calls": 8,
    "hide": ("chat_media_download",),

read_only_connection exists because X labels none of its tools. The general rule for a server's tools (a tool runs unasked only if the vendor labels it read-only and its name begins with a reading word) would have put every call to the owner. A connection that cannot write needs no label to say so. The entry's prompt tells the model to ask for small pages, to read a profile only when a post has earned it, and, if X refuses for lack of credit, to fall back to web search and mark each find that came from the web.

Estimating what a read cost

X's server does not say what a call cost. The program estimates it from what came back:

def estimate(spec: dict[str, Any], name: str, text: str) -> float:
    price = spec.get("price")
    if not price or name in price.get("free", ()):
        return 0.0
    try:
        data = json.loads(text).get("data")
    except (ValueError, AttributeError):
        return 0.0
    items = len(data) if isinstance(data, list) else (1 if data else 0)
    each = price["default"]
    for key in ("own", "people"):
        rate, marks = price.get(key, (None, ()))
        if rate is not None and any(m in name for m in marks):
            each = rate
            break
    return round(items * each, 4)

The result is written to the journal with estimated: True, and the ledger of {{ch:cost}} counts it toward the day's limit. A refusal ("Too many requests") parses to nothing and costs nothing. The bill is X's and has never been compared with this estimate.

Three refusals for a run with nobody watching

unattended in the same file wraps a service's run tool for a routine:

# Not app.decide: that answers "would this run unasked in a conversation?", and a small addition would.
if not app.reads(args):
    return no(f"Not done. Either that {title} tool changes something, and an unattended run may only read, or it has not been "
              "looked up yet with the find tool.")
taint = getattr(app, "taint", None)
seen = getattr(app, "unattended_seen", None)
...
if not own_store and taint is not None and taint.leaked(_foreign(args.get("arguments") or {}, seen)):
    return no(f"Not sent to {title}: the request contains details from the owner's mail, calendar or database, and nobody is here to "
              "approve sending them.")
left = getattr(app, "unattended_left", None)
if left is not None:
    if left <= 0:
        return no(f"No more reads of {title} in this run: the limit for an unattended run has been reached. Work with what you have.")
    app.unattended_left = left - 1
out = await run(args)
if not out.get("is_error"):
    seen.append(out["content"][0]["text"])

The first check asks reads() (in mcpapp.py, and in attio.py for the firm's database), which is true only for a tool the program has looked up and knows only reads. It deliberately does not ask the gate's decide. That answers a different question, "would this run unasked in a conversation?", and in a conversation a small addition to the firm's database (a note, a task, a comment) does run unasked. A routine that asked decide could therefore add to the database with nobody watching. The two questions differ where a conversation has an owner to read the report and a routine does not.

The second check has an exception. Everything a service returns is remembered as private, X included, because a timeline says something about its owner. A digest's second step is usually to look up the author of a post the first step returned, by the identifier X gave. Without the exception that lookup would be refused, since the identifier was "read from the owner's accounts". _foreign removes from the check any value the same service returned earlier in the same run: giving a service back its own identifier tells it nothing. A detail from the owner's mail in a search of X is still refused. The firm's database and the owner's meeting notes are exempt from the check altogether (own_store), because looking up there is the point.

A conversation makes the same check, with a question in place of a refusal. A read sent to a service that is somebody else's (X, a data vendor, a server the owner connected by its address) is checked for private details exactly as a web search is (McpApp._leak, called from McpApp.decide); if it carries any, the owner is asked, and shown the details recognised, before it goes. The same two exemptions apply: what the service itself returned earlier may be given back to it, and a store of the owner's own records is not checked.

Not repeating itself

In odysseus/schedule.py, after a message is sent, its text is kept:

data[job_id] = (data.get(job_id, []) + [text[:3000]])[-3:]
self._history_file.write_text(json.dumps(data, ensure_ascii=False), encoding="utf-8")

Only a delivered message is kept; a run that answered NO_REPLY or failed adds nothing. In odysseus/routines.py the next run is shown them:

before = ("\n\nWHAT THIS ROUTINE SENT THE LAST TIMES IT RAN, oldest first. Do not send an item again unless something about it has "
          "changed, and say what changed. If there is nothing new, say so in one line.\n" + "\n---\n".join(p[:1500] for p in previous[-3:])) if previous else ""

This is the one thing a routine carries from one run to the next, and it is a risk: the carried text was written from what strangers posted, so a planted sentence could reach a second run through it. The run it reaches still has reading tools only.

What public search can and cannot find

Web search finds companies that have announced themselves: a launch page, a news item, a post that a search engine has indexed. It finds them hours after X would, and it does not see the partner's own timeline or lists. That makes it a reasonable fallback for the digest, and a poor source for the signal that matters most to an early-stage investor: the person who left a job last week and has not yet said what they are doing. That person has no launch page. The signal exists only in records of who works where, which is what data vendors collect and sell. The vendor prompt in mcpapp.py says as much from the other side: if a vendor has no record of a company that has not raised, "that is common and means little".

A review of what leading assistants and venture firms connect to found few gaps in this system: it runs on a laptop where its rivals run in the cloud, it has no paid source of data about companies and people, it has no email address of its own, and only one copy runs, for one owner, where the firm wants one per partner. Only one of those costs real money, which is why a data vendor is the one significant purchase. The decision belongs to {{ch:build-or-buy}}: a database of companies and people is not something to build.

The evidence for which vendor to pay is thin exactly where this firm needs it. Little independent evidence exists: the one independent benchmark found covers a different region from the one this firm invests in. So the choice is made by measurement.

Choosing a data vendor by measurement

Seven vendors run servers of the kind {{ch:services-with-their-own-server}} connects, and each is an entry in APPS so the owner can connect it by name: Harmonic, Tracxn, Specter, Crunchbase, Crustdata, Evertrace and Dealroom. Their descriptions in the code differ in emphasis: some are strongest in one region, and Specter, Crustdata and Evertrace are described with signals such as job changes.

The method, in scripts/bakeoff.py and worked through in {{ch:build-or-buy}}, looks up companies the firm already knows in each vendor and counts what comes back, scored by code (found, people, funding, length of answer), looking up by website before name, since a name finds the wrong company. The firm's own records are the answer key. The test set is written from the firm's database, read only, and kept out of the repository because it is the firm's pipeline.

Designed around a daily limit. Several vendors' free tiers are understood to allow about a hundred reads a day (not checked; no vendor is connected). The limit is per vendor (90 by default, --limit to change it); every result is appended to a file as it arrives, and a later run skips rows already done. With the 29-company test set one run fits inside a free tier of about a hundred reads a day; a larger set would take a run a day, resuming where it stopped.

The design measures coverage, not truth. A vendor that returns a confident, wrong round scores the same as one that is right; the firm's own records seldom hold enough to tell. Checking a sample by hand would close part of that gap.

Data about people and where it comes from

The signal about a person leaving a job appears first on professional networks. What access those networks give programs has not been examined here, and neither has where any vendor gets its records of job changes. What follows is therefore an argument, not a finding, and it names no service and cites no shutdown. A vendor whose records come from collecting pages of a site whose rules forbid it depends on that site's tolerance, and the firm that buys from it inherits the dependency. What has been established is narrower and applies by analogy. For X, driving the website as the user is forbidden by its rules and risks the account; the sanctioned interface was chosen even though it charges per read. The same test applies to a vendor: ask how it gets its data, and prefer one whose answer does not rest on another company's forbearance.

A worked example: one morning, with X out of credit

Worked example: the live routine run

Input. scripts/live_routine.py runs one routine's instructions once, exactly as the scheduler would, with the real model and the real connected services, and sends nothing. The instructions were invented: find new companies in one sector. The X account had no credit.

Step 1. The routine agent starts with a fresh session, a fresh allowance of reads (eight of X, twelve of the database), the memory, and the instructions. It turns to X first.

Step 2. X refuses every read with "credits depleted".

Step 3. Following its instructions, the routine says in one line that X was unavailable and why, and makes one web search.

Step 4. It finds three launches, and notes that all three fall outside the day it was asked about.

Step 5. It looks two of them up in the firm's database, reading only, and finds neither. It writes "not checked" beside the third.

Output. One message: X was unavailable and why, then the three launches, with what the database showed for each. 38 seconds; about 1.3 cents, of which 0.6 the model and 0.7 the search.

The same instructions run once without the fallback sentence produced a message reporting X's refusal and listing nothing.

The run also showed three problems. Two of its four reads of the database failed on badly formed inputs, and a failed read still uses one of the twelve. It ended by offering to run again later, which a routine cannot do. And the fallback is a sentence in its instructions: the model followed it once.

The theory

The gate of an unattended run. A digest is an unattended run (Definition 3): there is no owner's decision d, so ask must become refuse. For a read sent to service s, the wrapper unattended computes

Gu(τ, x) = allow ⇔ reads(τ) ∧ (own(s) ∨ ¬leak(x ∖ Rs)) ∧ bs > 0; refuse otherwise

where reads(τ) holds only for a tool looked up and known to read, Rs is what s itself returned earlier in this run, leak is the fingerprint check of {{ch:untrusted-content}}, and bs is the reads left. The conversation's question, "would this run unasked?", is a different function, and it answers yes for a note added to the database. Using it here would have put add effects into A(T) for a run with nobody to read the report. Gu is sound for add, change, persist and destroy among tool calls; the history below is the program's own write. The only send it admits is the query of a read to another company, and only when that query carries no detail recognised from the owner's accounts.

Property: a routine's reads of a service are few and change nothing

Suppose bs is set to Bs when a run starts and every call to s passes through Gu. Then for every model, one run makes at most Bs calls to s (8 for X, 12 for the firm's database, 6 for a data vendor), and each is to a tool known to read.

Argument. The counter is read and decremented with no wait in between, before the call is made, and a call is refused when it is zero; the program's tasks share one thread, so two calls cannot both see the last unit. Each executed call therefore consumes one unit, including a call that then fails, which is why the bound is on attempts and why a badly formed read wastes one. The first conjunct admits only known reads.

Where it stops. The bound counts calls and says nothing of money. A call's cost is estimated from the items it returns, and the model chooses the page size, so the cost of one run is bounded only by Bs times the largest page the service allows times the price. And for X, "known to read" rests on the token's permissions, which the case note below shows had to be checked on the wire.

What crosses from one run to the next. Apart from memory, the only state is the history H: the last three delivered messages, shown to the next run at up to 1,500 characters each. So at most 4,500 characters of text with provenance S (written from strangers' posts) can enter a run from earlier runs. That bounds the amount and leaves the duration open: a planted sentence that each run repeats in its message survives indefinitely. "Do not repeat an item" is an instruction, so not repeating is a measurement, and it has not been made: no three consecutive days have run.

Choosing a vendor is an estimate. Run the bake-off as an evaluation in the sense of Definition 9 with n = 29 companies, k = 1, and yi = 1 if the vendor finds company i. Coverage Ȳ then has the percentile bootstrap interval over companies, and two vendors are compared by the paired difference on the same 29. With 29 cases, an interval for a coverage near 80% is roughly 14 points either side, so two vendors a few companies apart cannot be told apart. Two further limits are of construct, not of sample. The score is coverage, not truth: a confident wrong round counts as found. And the answer key exists only for companies the firm already knows, while a vendor's value to sourcing lies in companies it does not; coverage of the known stands in for discovery of the unknown, and no measurement here tests how well.

What goes wrong

Case note

The first sign-in link produced for X asked for every permission X offers: reading, and also posting, sending direct messages and changing billing. The entry listed seven reading permissions. The sign-in library had replaced that list with the server's full list of what it supports, because the protocol tells a client to ask for what the server advertises. Both were behaving as designed; together they turned "read only" into "everything". It was caught because the link was read before it was opened; no approval was given and no token saved. The program rewrites the link to ask for exactly the permissions the entry names, a test checks that a wider list is replaced and not added to, and the connect script prints what a sign-in asks for above the link. X's approval page then listed only reading, and the token returned carries the seven reading permissions and no others.

A wider rule counted one thing twice. The ledger had counted the cost of one tool, web search. Making it count any tool call that reports a cost made every browser run cost double, because a browser run's cost is already part of its task. An older browser test caught it, with 0.07 where 0.04 was expected. The rule names the exception.

An approval that did nothing. When the owner had the digest scheduled through the chat, the model wrote instructions of 972 characters; the schedule accepts 600. The owner was shown all 972, approved them, and only then did the schedule refuse. The length is checked while the question is built, and the tool's description gives the limit.

An approval that understated. The same question said a run "can only read (your mail and calendar, the web and my notes)". It could also read X, the meeting notes and the firm's database. The page lists every service a run can read, from the same list the run is built from. A description of a permission must be generated from the thing it describes.

How to test it

A test of an unattended reader must check refusals as carefully as successes, because the refusals are the design. tests/test_mcpapp.py checks that an unlooked-up tool and a changing tool are refused without a call reaching the service; that the third read is refused when the allowance is two, and the next run starts afresh; that a search carrying an address from the owner's mail is refused while X's own identifier may go back to it; that the owner's own notes are exempt; that the estimate is half a cent a post, a cent a profile, a tenth of a cent for the owner's own data and nothing for a refusal; and that a paid read is counted once and a browser run not twice. tests/test_schedule.py checks that a daily routine is shown its last three messages, across a restart, and that quiet or failed runs add nothing. tests/test_found_by_reading.py checks that an unattended run can only read even where a conversation would add unasked, and that a read sent to somebody else's service in a conversation is checked for private details as a web search is.

What none of this shows: any read of X that returned posts, so neither the estimate nor the limit of eight has met real data; three consecutive days of the digest, which is the only real test of not repeating; and whether the partner finds the finds worth reading.

What is proven and what is not

Verified, live: X connected with reading permissions only; 59 tools offered, one hidden, every one a read; the owner's own profile read through the gate in half a second. The digest routine run twice with invented instructions while X had no credit: the first reported the refusal and listed nothing; the second fell back to web search as described (38 seconds, about 1.3 cents). The scheduling fixes, by test; the routine itself was created live through the chat and has not run on its schedule.

Verified: seven vendors' addresses answer as servers of this kind, three at addresses their documentation gives and four at addresses on their own domains that were tried; one of the seven is not in the public registry. A test set of 29 companies was written from the firm's database, 28 with a website and 12 with people on record.

Not tested: the vendor comparison has not made a single lookup. No vendor is connected, since each needs an account that only the owner can open, and the script's choice of lookup tool has been tried only on invented tool names. Also not tested: any paid read of X; the cost estimate against X's bill; three days of the digest; and any claim here about data on people from professional networks.

Where this sits in the literature

The vendor comparison is an evaluation, and the statistics literature says what it should report. {{cite:miller2024errorbars}} argues that a result on a set of cases should come with a standard error or an interval, that correlated observations need clustered errors, that two systems run on the same cases should be compared by their paired difference, and that the number of cases should be chosen by a power calculation before the run. The bake-off as designed pairs vendors on the same companies, which agrees with that advice. It has no power calculation, and the published advice is stronger than this design on exactly that point: 29 companies were chosen because the firm had them, and the section on theory shows that they can separate only vendors far apart. The interval itself would be the bootstrap of {{cite:efron1979bootstrap}}, resampling companies, which needs no assumption about the shape of the distribution and is the method fixed in the model.

A sharper question is whether coverage measures what the firm needs. {{cite:bean2025construct}} reviewed hundreds of benchmarks and found recurring weakness in whether they measure the thing they are named for. The bake-off is open to that criticism twice over. It scores whether a record comes back, not whether it is right, and the chapter says so. And it can only be scored on companies the firm already knows, while the reason to buy a vendor is the company the firm does not yet know. The second gap is the deeper one, and nothing in the cited works says how to close it without an answer key for the unknown.

{{cite:kapoor2024agentsmatter}} argue that agent evaluations should report cost beside accuracy. The digest follows that in a small way, by estimating and recording the cost of every metered read, and the vendor comparison should follow it in a large way: a vendor's coverage means little without its price, and the chapter's own table of routes reports cost first.

Looking a company up by its website before its name is a choice in record linkage. {{cite:fellegi1969linkage}} decide whether two records are the same entity by how strongly each field's agreement indicates a match; a website is a field whose agreement is near decisive, while a shared name is weak evidence and produces false matches, which is the failure the chapter's method avoids by ordering the lookups.

The digest itself is a notification policy. {{cite:horvitz1999attention}} cast the decision to alert as a weighing of the value of the information against the cost of interrupting, given the person's attention; {{cite:mark2008interrupted}} found in an experiment that interrupted workers finished faster but with more stress and effort. The digest does none of the weighing. It arrives at a fixed hour, and its only concession to the cost of attention is that a run with nothing new may say so in one line or stay silent. Whether a morning message of this kind is worth its interruption has not been measured here.

Not repeating is related to, and different from, the problem {{cite:helland2012idempotence}} addresses. Messages delivered at least once must be processed so that a duplicate has no further effect, and the remedy is an identity that code can compare. The digest's duplicates are the same company found again by a different search, with no identity attached, and the comparison is left to a model reading its last three messages. Turning that into an identity code can check, such as a company's website, would make not repeating a property for the companies that have one.

Summary
  • Sourcing is mostly reading and matching, which a program can do; judging founders and being trusted by them it cannot.
  • A digest is a routine: nobody is watching, so every doubt is settled by code as a refusal: not a plain read, a detail from the owner's accounts, or reads used up.
  • X is connected to read only, by its read-only address and by reading permissions; the case note shows that the second must be checked on the wire.
  • Metered reads are counted and their cost estimated from the items returned; the estimate is marked as one.
  • When X refuses, the routine is told to say so and fall back to web search (followed once); web search is cheaper and later and cannot see the partner's own timeline.
  • An unattended run asks whether a tool only reads, not whether a conversation would run it unasked; in a conversation, a read sent to somebody else's service is checked for private details like a web search.
  • Keeping the last three messages sent stops repetition and is the one path from one run to the next.
  • Public search finds companies that announced themselves, not people who just left a job; that gap is why a data vendor is the one significant purchase, chosen by looking up companies the firm knows and counting what comes back. No lookup has been made.
Problems

Review

  1. List the three refusals a routine applies to a service read, and for each say what the gate would do instead in a conversation.
  2. Why does _foreign exempt values the same service returned earlier in the run? Construct a request that the exemption would wrongly let through, if any exists.
  3. A failed read of the database uses up one of the twelve. Change unattended so that a read rejected for badly formed inputs does not count, and write the test. What new risk does your change create?
  4. The history keeps the last three messages, cut to 1,500 characters each in the prompt. Argue for a different number or length, and say what evidence would settle it.
  5. Add a fifth column to the vendor comparison (its four are set out in {{ch:build-or-buy}}) that measures correctness rather than coverage on a small hand-checked sample. Describe the sample and how you would keep it out of the repository.
  6. Write the instruction for a routine that sends a digest only when something new and relevant appeared, using NO_REPLY. How would you test that it stays quiet on a day with nothing?
