Why it had to move

Through Chapters 6 to 12, Odysseus ran on its owner's own computer. For a program that only answers messages, that is merely inconvenient: it answers when the computer is on.

Chapter 8 changed the stakes. A reminder set for seven in the morning is worth nothing if the computer is asleep at seven. The design copes with that as well as it can, by sending a missed reminder late with a note saying so, and the chapter recorded plainly that "a scheduler runs only while that machine is awake". The only real fix is a machine that does not sleep.

Four things

Definitions
Image
A sealed package containing a program and everything it needs to run: the right version of the language, the libraries, the code. The same image runs the same way anywhere.
Machine
A small rented computer that runs one image.
Volume
A disk attached to a machine that keeps its contents when the machine is replaced.
Secret
A value, such as a key, that the hosting service stores encrypted and hands to the program when it starts, without its ever being written in the code or the image.

A deployment of Odysseus is exactly these four.

The division in the right-hand column is the point. Code changes often and is disposable. Data must never be lost by a change of code. Keys must never be in either. Chapter 7 put all of memory in plain files in one folder, and Chapter 8 put the schedule beside it; that decision now pays off, because "everything that must last" is one folder, and the volume is mounted exactly there.

A server with no door

Most programs on servers wait for connections from the internet, and so must have an address and an open port, and must be defended against everyone who finds it.

Odysseus opens no port at all. Chapter 1 noted that a Telegram bot can collect its messages by asking Telegram for them repeatedly, called long polling. Every connection the program makes is outward: to Telegram, to the model, to search, to the connector, to the browser vendor. Nothing on the internet can start a conversation with the machine, because there is nothing listening.

The configuration file says so by omission. It has no section describing a web service, and a comment explains that the absence is deliberate, so that nobody later adds one out of habit.

Long polling has one rule that matters here: only one program may poll for a given bot at a time. Two copies take messages from each other. The copy on the owner's computer was stopped before the server's copy started.

Two things that are easy to get wrong

The clock

Servers keep time in UTC. The owner does not live in UTC. Chapter 8 stored times as plain local date and time, "the same clock that stamps the owner's messages", and warned that if the program moved to a server elsewhere, nine in the morning must still mean the owner's nine in the morning.

On the owner's own computer this needed no thought, because the computer's clock was already the owner's. On the server it would have been silently wrong by five and a half hours: every reminder late, every message stamped with the wrong time, every "tomorrow" possibly the wrong day. The setting built in Chapter 8 for this moment pins the program's one clock to the owner's time zone, and the deployment sets it.

Who owns the disk

The image runs the program as an ordinary user and not as the all-powerful administrator, which limits what a fault in the program could damage. A freshly attached volume, however, arrives owned by the administrator, and an ordinary user cannot write to it. A program that cannot write its memory would fail at its first save.

So the machine starts with one line that runs as administrator, hands the data folder to the program's user, and then starts the program as that user. Verified On the server, the data folder and the files in it belong to the program's user.

One unknown, resolved

The agent library of Chapter 6 is not pure code. It carries a separate program inside it, built for a particular kind of computer. On the owner's computer that was the Windows version. Whether the right version would be installed in a Linux image, and would run there, could not be checked in advance, because the owner's computer has no tool for building images; the image was built by the hosting service.

Verified It was installed and it ran. The program connects to the agent library before it writes its start record, and the start record was written.

Two further gaps belong here. Nothing backs up the volume beyond whatever the hosting service does by default, so the owner's memory and schedule exist in one place. And nothing tells the owner if the machine stops: a dead assistant is silent, which is the one failure Chapter 8's rule about announcing failures cannot cover, because the thing that would announce it is the thing that has died.

Worked example: the second gap, five minutes later

The paragraph above was written before the deployment was tried by its owner. Within minutes it described a real event.

The machine was checked thirty seconds after launch and found running. At five minutes the hosting service stopped it, under a limit that applies to new accounts with no payment card. The copy on the owner's laptop had been stopped beforehand, correctly, so that two copies would not compete for messages. For some minutes no copy of Odysseus was running anywhere, and nothing said so. The owner found out by sending a message and getting no answer.

Three lessons, in order of generality. A check made at thirty seconds is evidence about thirty seconds. Stopping the old copy before the new one has proved itself removes the fallback at the moment it is most likely to be needed. And a system that announces its own failures still needs something outside itself to announce its death.

One fix was made at once, to a different gap the incident exposed: the log recorded that the server's one task had finished and did not record whether its reply was sent. Every reply is now recorded as sent or as failed. The watcher from outside is not built.

Summary
  • A scheduler needs a machine that does not sleep, so Odysseus was moved to a rented one.
  • A deployment is an image, a machine, a volume and secrets. Code is replaceable, data persists, keys are in neither.
  • The server opens no port. Every connection is outward.
  • The clock is pinned to the owner's time zone, and the data folder is handed to the program's user at start-up.
  • The program started on the server with everything connected, and was stopped by the hosting service after five minutes because the account has no payment card. It is back on the owner's laptop until that is settled.
Check your understanding
  1. Memory, the schedule and the log are kept on a volume and not inside the image. What would happen at the next update if they were in the image?
    Answer

    An update replaces the image. Everything written inside the running copy would be thrown away with it, so every update would wipe the owner's memory and schedule.

  2. Why is it safe for this server to have no firewall rules letting traffic in, when most servers need them?
    Answer

    Nothing on it listens for incoming connections. The bot asks Telegram for its messages, and every other connection is also started from the machine outward, so there is no door for a firewall to guard.

  3. The time zone setting is left out. The owner, at 10 in the evening local time, asks for a reminder "tomorrow at 7am". Describe what goes wrong.
    Answer

    The program believes the time is 4:30 in the afternoon, UTC. The message is stamped with that time, the model works out "tomorrow at 7am" from it, and the reminder is stored as 7:00 on the server's clock, which is 12:30 in the afternoon for the owner. It arrives five and a half hours late, and no error is reported anywhere.
