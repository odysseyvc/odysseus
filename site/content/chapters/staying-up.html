After this chapter you should be able to
  • Separate what an agent holds only while its process runs from what must be kept on disk, and say where each part of a conversation lives.
  • Explain why a task interrupted by a restart is announced to the owner and not resumed, and what the announcement must contain.
  • Handle messages that arrive while the program is down, without carrying out stale instructions.
  • Restart a program after its configuration changes using a supervisor, and explain why restarting inside the same process is not enough.
  • Describe a hosting arrangement with no inbound port, and say what changes when a service must call back to the program.
  • Name the two things that are easy to get wrong when moving such a program to a server.

The problem: an assistant that is there tomorrow

At ten past four the owner asks their assistant to draft a reply to a supplier. The draft appears, and they go into a meeting. While they are out, the program is updated, which means it is stopped and started again. At five they write "Looks good, send it." A program that kept the conversation only in its running memory now answers "Send what?". Worse things are possible. If the update had come in the middle of the sending, the owner would have no way to tell whether the email had gone, and a program that simply carried on might send it twice.

Restarts are not rare accidents. Every update is one, every crash is one, and on a laptop every lid closed is a kind of one. An agent that acts on its owner's behalf has to survive them without losing its place, without doing anything twice, and without leaving the owner to guess. It also has to run somewhere that stays awake, because a reminder set for seven in the morning is worth nothing if the computer is asleep at seven.

Where state lives

The first step is to sort everything the program knows into two piles: what vanishes when the process ends, and what is on disk.

Definitions
Process
One running copy of the program. Everything held in its variables (open connections, a task in progress, a question waiting for an answer) ends when it ends.
Session
One conversation as the agent library sees it: the sequence of messages and tool results the model is shown.
Transcript
The agent library's own file of a session, from which the session can be picked up again.
Resume
Starting the agent with the identifier of an earlier session, so that it continues that conversation instead of beginning a new one.
What survives a restart, and why.
ThingWhere it livesAfter a restart
Memory, the schedule, the journal ({{ch:the-conversation}})Files in the data folderKept
The conversationA small file holding the session's identifier, and the library's transcript, both in the data folderResumed
The record of private details read from the owner's accountsA file of short hashes in the data folderKept, so the check on what leaves through a search still works
Sign-in tokens for connected servicesFiles in the data folderKept
A task in progressThe processLost; announced to the owner
Messages waiting behind that taskThe process, with a copy of their first words in the journalLost; named in the announcement
An approval question on the owner's screenThe processDead, by design; the announcement says so

Two rows deserve a comment. The record of private details is kept on disk because the conversation is. Were it held only in the process, a resumed conversation would still have the owner's mail in front of the model while the check that stops mail leaving through a search had forgotten everything. The general lesson: once one piece of state outlives the process, every check that depends on it must outlive the process too. The second is the approval question. {{ch:the-gate}} explains that an approval covers exact inputs for one use and is held by the running program. Writing it to disk so that it could be honoured after a restart would let a tap made hours later approve something the owner can no longer see in context. It is allowed to die.

The design

The design answers five questions. For each, the obvious alternative and why it was not taken.

Five choices and their alternatives.
QuestionChoiceObvious alternative, and why not
How does a conversation survive?Keep the session identifier and the library's transcript in the data folder, and resumeRebuild the conversation from Odysseus's own journal. The library already knows how to resume; it had simply never been told the identifier.
What happens to an interrupted task?Announce it, with its first words, and do not carry it onResume it. The program cannot know how far it got, and an action done twice cannot be undone.
What happens to a message that arrives while the program is down?If it is more than ten minutes old on arrival, report it and do not actAct on it. An hours-old instruction may already have been done by hand.
How does the program restart itself?Exit with a special code; a supervisor starts a fresh processRestart inside the same process. Process-wide state, such as the tracing client, stayed shut.
How do messages reach a server?The program asks Telegram for them (long polling); no port is openA webhook, where Telegram calls the server. That needs a public address and a defended door.

Mechanism: a conversation that survives

The agent runner in odysseus/agent.py keeps the session's identifier in a file beside the rest of the data, and tells the agent library to write its transcript there too:

# The conversation outlives the program. Its id is kept in a small file beside the other data, and the agent
# library's own transcript is kept there too (CLAUDE_CONFIG_DIR below), so that on a server both are on the
# disk that survives an update. Before this, any restart began a new conversation without saying so.
self._session_file = settings.data_dir / "session.json"
self._transcripts = settings.data_dir / "agent"
self.session_id: str | None = self._load_session() if persist else None

The options passed to the library then include resume=self.session_id and an environment variable, CLAUDE_CONFIG_DIR, pointing at that agent folder. The second half is easy to miss. On a server, the library's usual place for transcripts is inside the image, and an update replaces the image. An identifier pointing to a transcript that no longer exists would be worse than no identifier. Keeping both on the disk that survives an update is what makes the identifier worth keeping.

The identifier is written after each task, when the library reports it, and deleted when the owner sends /new. A damaged file is read as "no conversation", not as an error. If the identifier is present but the session cannot be picked up, the runner starts a new one rather than failing every message from then on:

try:
    await client.connect()
except Exception as e:
    if self.session_id is None:
        raise
    # The saved conversation could not be picked up (its transcript is gone or unreadable).
    # Start a new one rather than fail every message from now on.
    self._journal.write("error", where="agent.resume", error=type(e).__name__, message=str(e)[:200])
    self.lost_session = True
    self.session_id, self._resumed, self._blank = None, False, True
    self._save_session()
    client = self._factory(options=self.options())
    await client.connect()

Setting _blank matters: it tells the conversation that the model has no context, so the owner's memory is shown again with the next message ({{ch:memory}}). The _resumed flag is used by the restart notice to say whether the earlier conversation was kept. lost_session is read by main after the client connects: when nothing was interrupted but the conversation could not be picked up, the owner is sent one line saying so (LOST_CONVERSATION in odysseus/__main__.py).

A conversation that never ends also grows without limit. The library condenses long conversations by itself, and the owner can send /new to start again on purpose. Memory, reminders and connections are untouched by /new; only the back-and-forth is dropped. {{ch:the-agent-loop}} explains condensing, and {{ch:cost}} what a long thread costs.

Mechanism: announce, do not resume

When the program starts, before it writes anything, it reads its own journal to find out what the last run left unfinished. The function is unfinished in odysseus/__main__.py:

for r in journal.read():
    if r["kind"] == "start":
        open_task, waiting = None, {}       # an earlier restart: whatever was lost then has been reported already
    elif r["kind"] == "task_start":
        open_task = {"preview": r.get("preview", ""), "asked": False}
    elif r["kind"] == "task_end" and "routine" not in r and "brief" not in r:
        open_task = None
    elif r["kind"] == "queued" and "q" in r:
        waiting[r["q"]] = r.get("preview", "")
    elif r["kind"] == "dequeued":
        waiting.pop(r.get("q"), None)
    elif r["kind"] == "queue_cleared":
        waiting = {}
    elif r["kind"] == "gate" and r.get("verdict") == "asked" and open_task is not None:
        open_task["asked"] = True
    elif r["kind"] == "gate" and r.get("verdict") in ("approved", "declined", "expired", "cancelled", "unasked") and open_task is not None:
        open_task["asked"] = False

This works because the conversation writes the right lines at the right moments. Each task begins with a task_start line carrying the first eighty characters of the request. Each message that has to wait behind a running task is written as queued with its own number and first words, and as dequeued when its turn comes. A start line marks each run of the program, so what was lost before an earlier restart is reported once, not at every later start. And the end of a routine or of a meeting brief is ignored (their task_end lines carry a routine or brief field), so work finishing in the background cannot hide an interrupted conversation task. Only the conversation writes task_start, so only its own task_end may close one.

Without the journal lines written before the work, there is nothing to find. A log that records only completions cannot tell a task that never started from one that died halfway.

Why not carry on? Because the program cannot know how far the task got. A tool call can succeed even though its reply never arrived: {{ch:a-changing-world}} calls this the lost acknowledgement. A restart is the same uncertainty at a larger scale. The email may have left in the last instant before the process stopped. Telling the owner costs one message; a duplicate email cannot be recalled.

The notice is sent to the owner after the agent client has connected, so that the program knows whether the conversation was resumed, and before the start line is written.

Worked example: a restart with work in flight

Worked example

Input. The owner asks "Summarise my inbox". While that task runs, they send three more messages. The summary is sent, the first waiting message is taken up, and the process is stopped while it runs. The journal ends like this (fields trimmed):

{"kind": "task_start", "preview": "Summarise my inbox"}
{"kind": "queued", "q": 1, "preview": "Remind me to call the plumber at 5"}
{"kind": "queued", "q": 2, "preview": "What is on tomorrow?"}
{"kind": "queued", "q": 3, "preview": "Book the dentist"}
{"kind": "task_end", "status": "done"}
{"kind": "dequeued", "q": 1}
{"kind": "task_start", "preview": "Remind me to call the plumber at 5"}

What each part does. At start, unfinished walks the journal. The first task_start opens a task. The three queued lines add three waiting messages. The task_end closes the first task. The dequeued line removes the first waiting message, and the second task_start opens the task that was cut off. No task_end follows it, so it is still open. No gate line says a question was asked. The result is the summary {"preview": "Remind me to call the plumber at 5", "asked": False, "waiting": ["What is on tomorrow?", "Book the dentist"]}.

The runner connects and finds session.json, so it resumes. restart_notice then builds the text.

Output. The owner receives:

I was restarted while I was working on something: "Remind me to call the plumber at 5". It was not finished, and I have not carried on with it by myself. 2 messages you sent were waiting behind it and were lost: "What is on tomorrow?"; "Book the dentist". Ask me again if you still want these done.

Had a question been on the owner's screen, the notice would add that the question "no longer counts, so tapping it will do nothing", because a button that silently does nothing looks like a fault. Had the conversation not been resumed, it would end with "I also no longer have our earlier conversation, only what I remember about you." A test in tests/test_durability.py checks the same counting on a shortened journal.

Messages that arrive while the program is down

Telegram holds messages for a bot that is not running and hands them over when it returns, for about a day; WhatsApp holds them for about a day and a half. That is convenient and dangerous. "Send the contract to the agent", written at nine and delivered at three, may have been done by hand in between, or may no longer be wanted.

So the Telegram wiring in odysseus/telegram.py checks the age of every message from the owner before passing it on:

user_id = message.from_user.id if message.from_user else 0
sent = message.date if message.date.tzinfo else message.date.replace(tzinfo=timezone.utc)
age = (datetime.now(timezone.utc) - sent).total_seconds()
if age <= STALE_AFTER_S or not conversation.is_owner(user_id):
    return False
loop_time = asyncio.get_running_loop().time()
if loop_time - told_late[0] >= 60 or told_late[0] == 0.0:
    told_late[0] = loop_time
    await TelegramChat(bot, message.chat.id).send("Something you sent earlier has only just reached me, because I was not running at "
                                                  "the time. I have not acted on it. Send it again if you still want it.")
return True

STALE_AFTER_S is 600 seconds. A message older than that on arrival is reported and not run. The owner is told at most once a minute, so a backlog of twenty messages produces one notice, not twenty. The WhatsApp channel has the same rule ({{ch:channels}}).

Two other kinds of thing arrive, or fail to, while the program is down. A reminder whose time passed is sent once on return, marked as late and saying why, and a repeating one moves to its next future time rather than firing once for each missed day ({{ch:acting-unasked}}). Events from the owner's mail and calendar that a watch was waiting for are simply missed: nothing goes back for them.

Restarting itself after a configuration change

Some changes need a restart. When the owner connects a new service from the chat ({{ch:services-with-their-own-server}}), the service brings new tools, and the set of tools is fixed when the agent client connects. The program has to start again to use them.

The obvious way is to restart inside the running process: stop polling, tear everything down, build it all again. That leaves behind anything that exists once per process and was shut by the first clean-up. A restart must begin from a new process.

Case note: a restart that dropped every trace

Restarting in place worked every time it was tried, in testing and in the owner's real chat. Every trace after the first restart was nonetheless silently dropped. The tracing client exists once per process, the first run's clean-up had shut it, and nothing reopened it. The live check of tracing runs one task in a fresh process, so it could not see this. No test found it; running the errand for real, connect after connect, did.

Definition
Supervisor
A small parent process whose only job is to start the real program as a child and decide, when the child exits, whether to start another.

A new process has none of the old one's history. So python -m odysseus starts a supervisor, which runs the program as a child marked by an environment variable:

def supervise() -> int:
    import os
    import subprocess
    env = {**os.environ, "ODYSSEUS_CHILD": "1"}
    while True:
        child = subprocess.Popen([sys.executable, "-W", "ignore", "-m", "odysseus"], env=env)
        try:
            code = child.wait()
        except KeyboardInterrupt:
            child.terminate()
            return 130
        if code != RESTART:
            return code

The child asks for a restart by exiting with the code RESTART, which is 75. Inside main, the function handed to the connector records the request and stops the Telegram poller one and a half seconds later; the clean-up in main's finally block closes every client, and main returns 75. Any other exit code, including a crash, ends the supervisor with that code, and whatever runs the supervisor (a terminal, or a host's restart policy) decides what happens next. The restart re-uses the mechanism above: the new child resumes the session, and because /connect is refused while a task is running, there is no interrupted task to announce.

Verified, live, in the owner's real chat with real servers, with the in-process restart that came before the supervisor: nine connects and disconnects in a row each ended with the assistant back in about twenty seconds, and after the last it used the new service. It was this run that showed traces were being dropped. The supervisor itself is verified by a unit test in tests/test_startup.py; no live restart through it is recorded.

Case note: a restart that failed on start-up code

One restart failed because of a wrong argument in the code that assembles the program at start-up. No test had caught it, because every other test builds its pieces by hand and never runs main. tests/test_startup.py was added for that reason: it runs main with stand-ins for Telegram and the agent client, once with every optional service configured and once with none. The lesson is general. The code that runs only at start is the code a restart depends on, and it needs a test of its own.

A restart is only as quick as the start

Every restart is a stretch in which the assistant cannot answer, so how long a start takes is part of staying up. Nobody had measured it. On the laptop it took about a minute from launch to the first message it could answer, and felt longer when the machine was busy.

The cause was found by writing the time at each stage of start-up into the start line of the journal, where it now stays. Almost all of the minute was the loading of libraries, in two avoidable places. The supervisor, a process whose whole job is to start the child and wait, was loading every library the child uses before starting it, and the child then loaded them all again: thirteen seconds spent twice. And the second reader of outgoing mail ({{ch:the-gate}}) loaded its own library while the program was starting, twelve seconds for something first needed minutes or hours later.

The supervisor now leaves before those libraries are reached, and the reader's library is loaded in the background once the program is already answering. A start measured after the change took 31 seconds. Verified, one start before and one after; the figures vary by several seconds with what else the machine is doing. What is left is the loading of three libraries the program cannot run without, and connecting the agent loop.

The lesson is the one from {{ch:cost}}, applied to time: a cost nobody writes down is a cost nobody reduces. The timing line cost four lines of code.

A home that stays awake

A program with a scheduler cannot live on a laptop: it does its scheduled work only while the laptop is awake. The fix is a rented machine that does not sleep. A deployment of Odysseus consists of four things.

Definitions
Image
A sealed package containing the program and everything it needs to run: the language version, the libraries, the code. The same image runs the same way anywhere.
Machine
A small rented computer that runs one image.
Volume
A disk attached to a machine that keeps its contents when the machine is replaced.
Secret
A value such as a key, stored encrypted by the hosting service and handed to the program as an environment variable when it starts, never written in the code or the image.
What a deployment consists of.
ThingWhat it holdsOn an update
ImageThe program and its libraries. No keys, no data, no tests, no website.Rebuilt and replaced
MachineOne shared processor and one gigabyte of memory, always onRestarted on the new image
VolumeThe data folder: memory, schedule, journal, session, transcripts, tokensUntouched
SecretsThe keys for Telegram, the model and each optional service, and the owner's Telegram identifierUntouched

The right-hand column is the point. Code changes often and is disposable. Data must never be lost by a change of code. Keys must be in neither. Because everything that must last is in one folder, the volume is mounted exactly there, and the image sets ODYSSEUS_DATA_DIR=/data.

No inbound port

Most programs on servers wait for connections from the internet, so they need an address and an open port, and must be defended against everyone who finds it. Odysseus opens none.

Definitions
Long polling
A way to receive messages by asking the service for them repeatedly; each request waits until there is something to return or a timeout passes. Every connection is started by the program.
Webhook
The reverse arrangement: the service calls an address the program publishes each time there is something new. The program must be reachable from the internet.

The Telegram bot uses long polling, and every other connection the program makes (to the model, search, the connector, the browser service) is outward too. Nothing on the internet can start a conversation with the machine, because nothing is listening. The hosting configuration says so by omission: fly.toml has no section describing a web service, and a comment explains that the absence is deliberate, so that nobody adds one out of habit.

Long polling has one rule that matters: only one program may poll for a given bot at a time. Two copies take messages from each other. The copy on a laptop must be stopped before a server's copy starts, which creates the gap described below.

When a service must call back

Two features break the "no door" property, in different ways.

The first is a channel that only works by webhook. WhatsApp's business interface calls the program each time a message arrives, so switching it on opens one port. {{ch:channels}} covers what that changes and how the calls are checked.

The second is subtler: a sign-in that returns to the program. Services with their own server are connected by a sign-in exchange in which the owner approves in a browser and the service then sends that browser back to an address on the machine the program runs on, such as 127.0.0.1, carrying a one-time code. The program listens on that port and waits up to ten minutes for the code. On a laptop where the owner is also reading the chat, this works. On a server it does not: the owner's phone cannot reach 127.0.0.1 on a machine in a data centre. A sign-in completes only on the machine the program runs on, and connecting from a phone cannot complete by design. Running it on a server would need a public return address, which is not built. {{ch:secrets-and-sign-ins}} covers the exchange itself and the ports a program opens for it.

Secrets and data on a host

Keys go into the host's secret store, imported from the local .env file, which is ignored by version control, never copied into the image and never shown to the model. The image runs the program as an ordinary user rather than the administrator, which limits what a fault could damage.

The data folder is the sensitive part. Once the conversation is saved, mail text the model has read is on disk in the clear, in the transcripts. A data folder inside a folder that a file-syncing service copies to its own servers means another company holding the owner's mail, chosen by nobody; this happened on the owner's laptop, and moving the folder out did not recall the copies already taken. So the program warns at start-up if its data folder is inside a synced one, and every agent, including the unattended ones, writes its transcript inside the data folder and nowhere else. Nothing backs up the volume beyond whatever the host does by default.

Two things that are easy to get wrong

The clock

Servers keep time in UTC. The owner does not live in UTC. On a laptop this needs no thought, because the laptop's clock is already the owner's. On a server, a program that reads the machine's clock is silently wrong by the owner's offset: every reminder late, every message stamped with the wrong time, every "tomorrow" possibly the wrong day, and no error anywhere. For an owner five and a half hours ahead of UTC, "remind me at 7am" fires at half past twelve.

The fix is one clock for the whole program, pinned to the owner's zone by a setting. In odysseus/config.py:

def make_clock(tz: str = ""):
    """The one clock used for message stamps, memory dates and the schedule: local wall-clock time, no zone."""
    if not tz:
        return datetime.now
    from zoneinfo import ZoneInfo
    zone = ZoneInfo(tz)
    return lambda: datetime.now(zone).replace(tzinfo=None)

main builds this once and passes it to everything that needs the time. The daily budget uses the same zone, so "today" ends at the owner's midnight. The hosting configuration sets ODYSSEUS_TZ, and the deploy guide tells anyone copying it not to skip that line.

Who owns the disk

A freshly attached volume arrives owned by the administrator, and the program runs as an ordinary user who cannot write to it. A program that cannot write its memory fails at its first save. So the image's start command runs one step as administrator, hands the data folder to the program's user, and then starts the program as that user:

CMD ["sh", "-c", "chown -R app:app /data && exec runuser -u app -- python -W ignore -m odysseus"]

Verified On the server, the data folder and the files in it belonged to the program's user.

What goes wrong

Two failures have been described already: restarting in place, which left process-wide state shut and failed silently, and start-up code that no test ran. Three more follow.

A dead assistant is silent

Case note: five minutes on a server

The program was deployed to a hosting service and started there. It wrote its start record to the mounted disk, showing mail, the browser and file reading connected, and handled one message. The machine was checked thirty seconds after launch and found running. At five minutes the hosting service stopped it, under a limit on new accounts with no payment card. Nothing in the deploy output said so; the only trace was a line in the machine's log. The copy on the owner's laptop had been stopped beforehand, correctly, so that two copies would not compete for messages. For some minutes no copy was running anywhere, and nothing said so. The owner found out by sending a message and getting no answer.

Three lessons, in order of generality. A check made at thirty seconds is evidence about thirty seconds. Stopping the old copy before the new one has proved itself removes the fallback at the moment it is most likely to be needed. And a system that announces its own failures still needs something outside itself to announce its death.

The incident exposed a second gap. The journal recorded that the server's one task had finished and not whether its reply was sent, so whether that reply arrived is unknown. A record of finishing is not a record of delivery: every reply is recorded as sent, with the number of parts, or as failed, with how many parts got out. The watcher from outside is not built.

A lost conversation must be said

When a saved session cannot be resumed, the runner writes an error to the journal and starts afresh. If the owner heard of this only when a restart had also interrupted a task, a quiet restart with a damaged transcript would leave the owner's next "Looks good, send it" facing a model with no idea what "it" was. So the program sends one line in that case too: it was restarted, could not pick up the earlier conversation, and still has what it remembers. The memory block is shown again, so lasting facts survive; the thread does not.

Waiting messages must be written down

The owner of a message queued behind a task has been told "Noted. I'll do this as soon as the current task is finished." Held only in the process, that promise would vanish in a restart without a word. So each waiting message is journalled as queued, so that a restart can name it in the notice.

How to test it

A test of this part must check that state survives a new process reading the same files, that what cannot survive is announced, and that the program can assemble itself at all. The tests use a trick worth copying: a "restart" is simulated by building a second runner or conversation on the same folder, which is exactly what a new process does, without starting one.

  • tests/test_durability.py (eleven tests) covers the waiting queue and stop, /new, the session identifier being saved, picked up and passed as resume with transcripts inside the data folder, a damaged session file, and every case of the restart notice described above.
  • tests/test_startup.py checks that the program assembles with everything and with nothing optional, and that the supervisor starts a fresh child each time one exits with 75 and stops on any other code.

What the tests do not show: that the library actually resumes a real session, that the notice reaches a phone after a real restart, or that anything works on a real server. Those need live runs. One exists for resuming: an evaluation scenario in which the owner says "Looks good, send it" after a restart sent the email shown before the restart, in two runs with the real model ({{ch:a-changing-world}}). Without the kept session, the agent could only ask what "it" was.

What is proven and what is not

Verified The sixteen tests in tests/test_durability.py and tests/test_startup.py pass. Resuming a conversation after a restart worked in an evaluation scenario with the real model, two runs. Restarting in place worked live nine times in a row; the supervisor that replaced it is tested by a unit test only. The image built, and the program started on a hosting service, connected to the agent library, wrote to its volume as the right user, and handled one message.

The program has not run on a server for more than five minutes. That deployment was stopped by the host because the account had no payment card, and the program runs on the owner's laptop. Whether the reply to the server's one message was delivered is not known. No scheduled job is recorded firing at its real time on either machine.

Not tested A restart through the supervisor in the real chat. The restart notice reaching the owner's phone after a real restart mid-task. Memory and the schedule surviving a restart of the server's machine. A reminder firing at the right local time on a server. Whether one gigabyte of memory is enough. A conversation kept for weeks. Cost counted correctly across a resume: the library reports a running total per session, and whether it continues after a resume has not been measured ({{ch:cost}}). The stale-message rule for Telegram: it is written and has no test, because the stand-in for Telegram does not carry dates (the WhatsApp version has a unit test). Not built: a public return address for sign-ins, a backup of the volume, and anything outside the program that notices when it has died.

Summary
  • Sort state into what dies with the process and what lives on disk. Put everything that must last in one data folder, and make every check that depends on surviving state survive too.
  • A conversation survives if two things are kept where data survives: the session identifier and the library's transcript. If it cannot be picked up, start a new one rather than fail every message.
  • An interrupted task is announced, with its first words and any messages that were waiting, and not resumed: the program cannot know how far it got, and doing something twice cannot be undone. Approvals die with the process, and the notice says so.
  • A message more than ten minutes old on arrival was written for a moment that has passed. Report it; do not act on it.
  • Restart by exiting to a supervisor that starts a fresh process. Restarting in place leaves process-wide state behind.
  • Long polling needs no inbound port. A webhook channel opens one, and a sign-in that returns to the program completes only on the machine the program runs on.
  • Pin the clock to the owner's zone, and hand the data disk to the program's user at start. Then check again after ten minutes, not thirty seconds.
