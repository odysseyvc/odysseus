Status of this chapter

Three ways the first design lost work

Chapter 6 made two choices in the name of a small first slice. One task runs at a time, and a second message is turned away. The conversation lives in the running program's memory. An independent reading of the code later listed what those choices cost, and the evaluation of Chapter 15 showed one of them happening.

What was lost, and when.
SituationWhat the first design didWhat the owner experienced
A second message during a taskReplied "Still working on the last task" and discarded itHaving to remember to send it again. During an approval wait or a browser run, that could be ten or fifteen minutes.
The program restarts between messagesBegan a new conversation, silently"Looks good, send it" answered with "send what?"
The program restarts during a taskNothing. The task and any approval question simply ceased to exist.Silence, and no way to tell whether the thing was done

A restart is not a rare accident. Every update to the program is one (Chapter 13), and so is every crash.

Waiting a turn

A message that arrives while a task is running is now kept and answered with one line saying so. When the task ends, the waiting messages run one at a time in the order they arrived. Up to five can wait.

Three details matter more than the mechanism.

  • Commands do not wait. "stop", /status and the rest are handled by code the moment they arrive, as before. A queue that could delay "stop" would be worse than no queue.
  • "Stop" drops what is waiting too, and says how many. An owner who types "stop" wants things to stop. If the waiting messages ran next, "stop" would have ended one task and started another.
  • A typed "yes" during an approval question is still only a message. It waits its turn like any other and approves nothing (Chapter 9).
Tasks still run one after another, not side by side. A long browser run still holds up what is behind it. Running work in the background is a separate change and is not built.

Where a conversation lives

Definitions
Session
One conversation as the agent library sees it: the sequence of messages and tool results that the model is shown.
Transcript
The library's own file of a session, from which the session can be picked up again.
Resume
Starting the agent with the id of an earlier session, so that it continues that conversation and does not begin a new one.

The agent library already knew how to resume. It was never asked to, because the id of the session was held in a variable that vanished with the program. Two things are now kept beside the rest of Odysseus's data: a small file holding the session's id, and the library's transcript, which it is told to write there instead of in its usual place.

The second of those is easy to miss. On a server, the library's usual place is inside the image, and an update replaces the image (Chapter 13). An id that pointed to a transcript that no longer exists would be worse than no id. Keeping both on the disk that survives an update is what makes the id worth keeping.

If the saved session cannot be picked up, because its transcript is missing or damaged, the program starts a new conversation and carries on. The alternative would be failing on every message until someone noticed.

A conversation that never ends has its own cost: it grows. The library condenses a long conversation by itself (Chapter 7), and the owner can now also send /new to begin again deliberately. Memory, reminders and connections are untouched by /new; only the back-and-forth is dropped.

An interrupted task is announced, not resumed

When the program starts, it reads its own log for a task that was started and never finished. If there is one, the owner is told, with the first words of the request so they know which:

Worked example: the notice after a restart

The owner asked for a meeting to be moved. The question "Change this event and email the change to its guests?" was on their screen when the server was updated. On starting again, the program sends:

I was restarted while I was working on something: "Move my 1:1 with Sam today to 4pm". It was not finished, and I have not carried on with it by myself. I had asked for your approval; that question no longer counts, so tapping it will do nothing. Ask me again if you still want it done.

Why not simply carry on? Because the program cannot know how far the task got. Chapter 15 introduced the lost acknowledgement: an action that happened although its call reported failure. A restart is the same uncertainty at a larger scale. The email may have been sent in the last instant before the program stopped. Running the task again could send it twice. Telling the owner costs one message; a duplicate cannot be taken back.

The old approval question is dead for a reason from Chapter 9. Approvals are held by the running program, and an approval covers exact inputs for one use. After a restart nothing holds them, so a tap on the old buttons finds nothing waiting. The notice says so, because a button that silently does nothing looks like a fault.

Summary
  • A message that arrives during a task waits its turn. Commands never wait, and "stop" empties the queue.
  • A conversation survives a restart if two things are kept where data survives: the session's id and the library's transcript.
  • If the saved conversation cannot be picked up, start a new one and carry on.
  • A task interrupted by a restart is announced, not resumed: the program cannot know how far it got, and doing something twice cannot be undone.
  • Approvals do not survive a restart, by design. The owner is told that the old buttons no longer count.
Check your understanding
  1. The session's id is kept on the disk that survives an update, and the transcript is left where the library normally writes it. What happens at the next update?
    Answer

    The update replaces the image, and the transcript with it. The program starts with an id that points to nothing. If that case is not handled, every message fails. Here it is handled by starting a new conversation, but the owner still loses the old one, which was the thing being protected.

  2. The owner sends three messages during a long task and then "stop". Which of the four things happen?
    Answer

    The running task is ended and the three waiting messages are dropped. The owner is told the task was stopped and that three waiting messages were dropped. None of the three runs.

  3. Give a case in which resuming an interrupted task automatically would do harm.
    Answer

    The task was "email Ravi about the tap". The email left, and the program was stopped before it recorded that. On starting again it sees a task with no end, runs it again, and Ravi gets the email twice. Nothing in the log could have told it the first one had gone.
